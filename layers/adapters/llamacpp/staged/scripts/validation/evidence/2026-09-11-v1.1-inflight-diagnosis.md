## 2. MI250: 직렬화 관측은 유지, open-batch 상한 인과는 미확정

모델은 두 실행 모두 Step-3.7-Flash-Q4_K_XL, 45층이다. 아래 TPS는 artifact의
생성 토큰 합계 / `elapsed_ms`이며 적재 성능·정상 응답으로 승인한 유효 TPS가 아니다.

| 조건 | 8-stage / 한 머신 | 16-stage / 두 머신 |
| --- | --- | --- |
| resident / 요청 수 | 256 / 256 | 16 / 16 |
| 요청별 context 상한 | 512 | 100512 |
| 실제 입력 | 총 10160토큰, 요청당 평균 39.7 | 100000토큰 1건 + 61토큰 15건 |
| 출력 상한 / 종료 | 64 / 전부 length | 512 / ignore_eos=true, 전부 length |
| batch / ubatch | 512 / 512 | 512 / 512 |
| 완료 / 해제 | 256 / 256 | 16 / 16 |
| 생성 토큰 / 시간 | 16384 / 54.318s | 8192 / 1072.206s |
| generated TPS | 301.63 | 7.64 |
| 요청 묶음 | 32요청씩 서로 다른 8개 묶음 | 513개 배치는 16요청, 이후 201개는 1요청 |
| idle_gated 합계 | 0 | 0 |

따라서 **301.63 → 7.64를 노드 수 증가의 손실률로 계산할 수 없다.** resident, 입력 길이,
출력 길이, EOS 조건, KV 크기가 함께 바뀌었다. 16건 모두 실제 100k prefill한 실행도 아니다.

16-stage의 전형적 배치는 `497 prefill + 15 decode`(200회)다. 같은 요청의 decode는
이전 토큰 반환 전 발행할 수 없고, 기본 prefill fragment 창도 1이다. 한 배치가 16요청을
모두 점유하면 다음에 발행할 독립 요청이 없어진다. 8-stage의 32요청 묶음 8개와 대조된다.
이는 **요청을 한 묶음에 소진하는 정책과 요청 의존성의 결합**을 우선 검사할 근거다.

원본 `stage-overlap-diagnosis.json`의 평균 0.8618/16, 단일 활성 86.1576%는
호스트별 Unix 시각을 보정 없이 합친 **RPC 구간**이다. GPU 계산 겹침이나 정확한 전역 비행 수가 아니다.
시계를 섞지 않고 머신별 8개 stage를 재집계하면 다음과 같다.

| 머신 | 자체 분석창 | 평균 동시 RPC | 최대 동시 RPC |
| --- | --- | --- | --- |
| MI250-01 | 1071.329s | 0.42535 | 1 |
| MI250-02 | 1065.803s | 0.43877 | 1 |
| 8-stage 비교 실행의 한 머신 | 54.172s | 5.84174 | 8 |

각 머신 내부 직렬화는 이 재계산으로도 유지된다. 다만 현재 `max_open_batches` 기본값은
0(상한 비활성)이며 실제 프로세스의 유효 환경변수는 자료에 봉인되지 않았다.
gate 거절 0과 함께 보면 **open-batch 설정이 차단 원인이라는 선언은 보류**해야 한다.
현재 event adapter에서 `queue.is_running()` 호출도 찾지 못했다. 이름만으로 제거할 대상이 아니다.

머신 간 7→8의 관측 간격 평균은 19.3515ms다. 미보정 전체 batch 지연 1491.438ms와 단순 비교해도
약 1.30%다. 이 값에는 시계 오차·큐·전달이 섞인다. ping RTT나 baseline 차감으로
“실제 네트워크 비용 1% 미만”을 확정하지 않는다. 다른 사용자 부하가 있었던 MI250-01의 GPU 표본도 분리해야 한다.

| 16요청 혼합 arm | batch / ubatch | generated TPS | 100k 요청 TTFT |
| --- | --- | --- | --- |
| 기준 | 512 / 512 | 7.640 | 843.442s |
| 논리 폭 증가 | 2048 / 512 | 6.718 | 972.188s |
| 논리·물리 폭 증가 | 2048 / 2048 | 5.348 | 1269.162s |

각각 단회다. 마지막 비교는 UBATCH 하나만 바꾼 실험이 아니다. 큰 폭이 최선이라는 근거는 없지만
이 세 점으로 최적 폭도 정할 수 없다. 모든 출력이 length이고 사실을 지어낸 응답도 있어 서비스 품질 승인은 없다.
기존 MI250 artifact에는 `output_received_ms`가 없어 실제 토큰 간격 분포도 재구성할 수 없다.

## 3. Hy3: 긴 prefill의 지연 전파와 보관 메모리

Hy3 Q5_K_S 191.884GiB, 80층, 5호스트/6stage다. M42의 3090 두 장, Spark,
Mac Metal, 로컬 3090, Ubuntu 2070에 걸쳤으며 CPU expert 오프로딩을 포함했다.
resident 8, 요청별 context 102400, batch/ubatch 512/256, open-batch 8, fragment 1.
실제 입력 길이 31643/63682/91696, 두 웨이브 총 16건/966748토큰, 출력 상한 8192였다.
6시간 deadline에 16건 전달, 4건 완료·해제, 12건 미완료, OUTPUT 16438건으로 실패했다.
완료 4건도 산술 검사는 통과했지만 서술 품질/분량 조건은 실패해 유효 TPS 승인은 없다.

| 파생 관측 | 결과 / 해석 |
| --- | --- |
| 같은 요청 연속 OUTPUT 간격 | 16430쌍을 decode 입력 위치와 연결, 미연결 0 |
| 초기 prefill 혼합 구간 | 간격 중앙 29.790s; head issue 창 186.65분 |
| decode-only 구간 | 간격 중앙 1.869s; head issue 창 53.60분 |
| 후기 prefill 구간 | 간격 중앙 31.150s; head issue 창 119.65분 |
| decode-only batch인데 20초 이상 출력 공백 | 1963건 모두 이전/현재 head issue 사이에 prefill 포함 batch 존재 |
| 동일 91696토큰 입력의 편차 | 요청 3: prefill 428회, TTFT 186.46분; 요청 6: 240회, TTFT 92.91분 |
| 최초 stage prefill 비용 | native execute 평균 6872.08ms / RPC 평균 6899.91ms; parse 0.734, match 0.484, encode 5.387ms |
| decode 묶음 | 대부분 3요청/5요청 두 묶음. resident 8로 decode 256행 채움은 불가능 |

시간창과 표본 수가 다른 통계를 나눠 TPS를 만들지 않는다. native execute에는 CPU/GPU/전송이
섞여 있어 커널 계산 비용으로 부르지 않는다. prefill은 M42, decode는 Spark의 RPC가 가장 길었다.
tail 한 단계나 배치 행 수만으로 전체 비용을 예측하기 어렵다.

첫 stage가 발행한 payload 합은 10908855372B(10.15966GiB)다. 입·출력 full payload를
두 번 보관하면 약 20.3193GiB이고 Spark agent 최종 RSS는 약 20.546GiB였다.
broker의 full-event receipt 보관과 일치하는 강한 후보이나 heap 귀속을 입증한 값은 아니다.
**활성 flight 제한과 이미 끝난 receipt의 보관 제한은 별도 예산**이어야 한다.

## 6. 후속 구현 — bounded ordinary 선택 후보 (2026-09-11)

계획 커밋 `974350c27`은 GitHub `main`에 push 확인 후 구현을 시작했다.
아래는 §5의 문서 전용 변경 뒤에 수행한 별도 작업이다. 실제 GPU 배포/성능 승인은 포함하지 않는다.

### 선택 계약과 사용 범위

현재 event worker가 `Scheduler::prepare_plan_with_limits`를 호출한다. 검증된 native issue 수락 뒤에만
policy state를 commit하므로 거부/준비 취소로 공정성 순서를 소비하지 않는다.
기존 KV/flight/원장 승인 경로, decode outstanding≤1, node별 native 호출 직렬성은 유지한다.

| agent 시작 시 환경변수 | 의미 / 기본값 |
| --- | --- |
| `P4_STAGED_DECODE_MEMBERS` | 한 배치의 decode 요청 수 상한 / 0(축 제한 없음) |
| `P4_STAGED_PREFILL_MEMBERS` | 한 배치의 prefill 요청 수 상한 / 0 |
| `P4_STAGED_PREFILL_ROWS` | 한 배치의 prefill 총 행 상한 / 0 |
| `P4_STAGED_PREFILL_ROWS_PER_REQUEST` | 한 요청에서 발행할 prefill 행 상한 / 0 |

모두 0이면 기존 선택 경로를 그대로 사용한다. 하나라도 설정하면 ordinary attention에만 새 선택을 적용한다.
atomic verify/replay가 대기 중이거나 equal-sequence 모델이면 기존 선택을 사용하고 진단에 적용 여부를 남긴다.
값은 선택 상한이며 메모리 예약/credit이 아니다. resident/open/fragment 상한이나 전역 byte 상한을 올리지 않는다.
유효하지 않은 숫자 문자열은 기존 환경설정 방식과 같이 0으로 읽히므로 artifact의 유효값을 확인한다.

예를 들어 resident16의 판별 후보 `(decode_members=4, prefill_members=4, prefill_rows=128,
prefill_rows_per_request=64)`는 16 decode 또는 16 장기 prefill을 한 번에 모두 소비하지 않는다.
이는 최적값/실기 권장값이 아니며, 현재 예산 범위의 실험 후보다. coalescing/open 설정도 함께 봉인한다.

phase별 sequence ID 재개 위치를 보존해 eligible 벡터 길이가 변해도 다음 요청을 건너뛰지 않는다.
prefill에는 선택된 요청 사이의 순환 배분과 총량/요청별 상한을 적용한다. capacity>1이면 대기 prefill에
최소 1행의 기회를 남기고, capacity=1에서는 지속 decode 8회 후 prefill 기회를 부여한다.
이것은 **수락된 선택 기회 기준의 기아 방지**다. 시간 기반 aging·누적 비용 deficit·native 비용 예측은 아직 구현하지 않았다.

### 관측 계약

`BatchObservation.scheduling`은 선택 시점의 유효 설정·적용 여부·open 수·수용 대기 수·outstanding 차단 수·
입력 부재 수·phase별 eligible 요청 수를 보관한다. node 전체 집계이며 요청별 stall trace나 GPU 유휴 원인 확정값이 아니다.
기존 producer의 필드 부재는 `None`이며 0 측정으로 해석하지 않는다. issue가 전혀 나지 않은 구간의 원인은 아직 담지 못한다.
