## 2. MI250: the serialization observation stands; the open-batch cap as cause is unconfirmed

Both runs used Step-3.7-Flash-Q4_K_XL, 45 layers. The TPS below is the artifact's
total generated tokens / `elapsed_ms`; it is not a useful TPS approved for load performance or valid responses.

| Condition | 8-stage / one machine | 16-stage / two machines |
| --- | --- | --- |
| resident / requests | 256 / 256 | 16 / 16 |
| Per-request context cap | 512 | 100512 |
| Actual input | 10160 tokens total, 39.7 per request on average | 1 request of 100000 tokens + 15 requests of 61 tokens |
| Output cap / termination | 64 / all length | 512 / ignore_eos=true, all length |
| batch / ubatch | 512 / 512 | 512 / 512 |
| Completed / released | 256 / 256 | 16 / 16 |
| Generated tokens / time | 16384 / 54.318s | 8192 / 1072.206s |
| generated TPS | 301.63 | 7.64 |
| Request grouping | 8 distinct groups of 32 requests each | 513 batches with 16 requests, then 201 with 1 request |
| idle_gated total | 0 | 0 |

Therefore **301.63 → 7.64 cannot be computed as a loss rate from adding nodes.** Resident count, input length,
output length, EOS condition, and KV size all changed together. Nor was this a run in which all 16 requests actually did a 100k prefill.

The typical 16-stage batch is `497 prefill + 15 decode` (200 times). A decode for a request cannot be issued
before its previous token has returned, and the default prefill fragment window is also 1. When one batch takes all 16 requests,
there is no independent request left to issue next. This contrasts with the 8-stage run's 8 groups of 32 requests.
This is the reason to check first **the combination of a policy that exhausts requests in one group and request dependency**.

The original `stage-overlap-diagnosis.json` values, a mean of 0.8618/16 and 86.1576% single-active, are
**RPC intervals** merged from per-host Unix times without correction. They are not GPU compute overlap or an exact global in-flight count.
Re-aggregating each machine's 8 stages without mixing clocks gives:

| Machine | Own analysis window | Mean concurrent RPC | Max concurrent RPC |
| --- | --- | --- | --- |
| MI250-01 | 1071.329s | 0.42535 | 1 |
| MI250-02 | 1065.803s | 0.43877 | 1 |
| One machine of the 8-stage comparison run | 54.172s | 5.84174 | 8 |

Serialization inside each machine still holds under this recomputation. However, the current `max_open_batches` default is
0 (cap disabled), and the actual process's effective environment variables were not sealed in the data.
Taken together with 0 gate rejections, **any claim that the open-batch setting is the blocking cause must be withheld**.
We also found no `queue.is_running()` call in the current event adapter. It is not something to remove on the strength of its name alone.

The mean observed interval for the cross-machine 7→8 hop is 19.3515ms. Even compared naively with the uncorrected total batch latency of 1491.438ms,
it is about 1.30%. This value mixes clock error, queueing, and delivery. Ping RTT or baseline subtraction does not
establish "actual network cost below 1%". The GPU samples from MI250-01, which carried load from other users, must also be separated.

| 16-request mixed arm | batch / ubatch | generated TPS | 100k request TTFT |
| --- | --- | --- | --- |

## 3. Hy3: latency propagation and retained memory in long prefill

Hy3 Q5_K_S, 191.884GiB, 80 layers, 5 hosts/6 stages. It spanned the two 3090s in M42, Spark,
Mac Metal, the local 3090, and the Ubuntu 2070, and included CPU expert offloading.
resident 8, per-request context 102400, batch/ubatch 512/256, open-batch 8, fragment 1.
Actual input lengths were 31643/63682/91696, two waves totaling 16 requests/966748 tokens, output cap 8192.
It failed at the 6-hour deadline with 16 requests delivered, 4 completed and released, 12 incomplete, and 16438 OUTPUTs.
The 4 completed requests passed the arithmetic check but failed the narrative quality/length condition, so no useful TPS is approved.

We do not build TPS by dividing statistics with different time windows and sample counts. native execute mixes CPU, GPU, and transfer,
so we do not call it kernel compute cost. The longest RPC was M42 for prefill and Spark for decode.
Total cost is hard to predict from a single tail stage or batch row count alone.

The sum of payloads issued by the first stage is 10908855372B (10.15966GiB). Retaining the full input and output payloads
twice gives about 20.3193GiB, and the Spark agent's final RSS was about 20.546GiB.
This is a strong candidate consistent with the broker retaining full-event receipts, but it is not a value that proves heap attribution.
**Limits on active flights and limits on retaining already-finished receipts must be separate budgets.**

## 4. Fix boundaries the code points to

| Owner / path (repository-relative) | Current behavior and constraint it places on the plan |
| --- | --- |
| adapter `src/v2/scheduler.rs::plan_ordinary` | Gives 1 row to each ready decode, then allocates the remaining width to prefill. Dividing among current requests is not the same as fairness over cumulative wait/service |
| adapter `src/v2/node/state.rs::phase_within` | Prefill uses the fragment window; decode is blocked while outstanding>0. The decode dependency stays |
| adapter `src/v2/node/worker/drive.rs` | Owns the issue-row cap, open/min gate, and issue commit. A small row cap alone cannot split 16 decodes into several groups |
| adapter `src/v2/node/worker.rs::stage_request` | Waits synchronously on native requests. A change that allows concurrent calls on the same context must be separated from actor responsiveness |
| native `server/src/server/server_physical.cpp` | Finishes the first stage's physical execution and capture and the processing of subsequent physical capsules, then encodes the whole result. Splitting logical512 into physical256 alone does not send the half that finished first |
| adapter frontier/flight/physical_receive | Owns token range, stage prefix, settlement, and reservation. Accepting different execution IDs is not a proof of KV ordering safety for the same sequence |
| `layers/agent/src/event_broker/ledger.rs`, `event_broker/mod.rs` | Retains full Events, count-based limits. Change to a neutral payload byte/receipt lifetime contract; no KV/llama types in core |

The common prefix of the adapter/native paths is `layers/adapters/llamacpp/staged/`, and the adapter is `adapter/` under it.
We do not cite the equal-sequence path's `PREFILL_PATIENCE` as a fix for the ordinary path.
Backend calls stay at 1 per node, and progress of independent batches on other stages is allowed separately.
Issuing prefill ahead is not safe merely because the input tokens are known. It is widened only after proving the per-stage KV prefix, retransmission,
recurrent auxiliary state, and fragments left over during cancellation.

This diagnosis is **the common basis for fixing serialization, latency, and memory**. It does not declare GPU saturation, an optimal batch, or a throughput improvement rate.
The order for moving to implementation and real-hardware approval follows the roadmap's v1.1 plan.

## 6. Follow-up implementation — bounded ordinary selection candidate (2026-09-11)

Implementation started after confirming that plan commit `974350c27` was pushed to GitHub `main`.
The following is separate work done after the documentation-only change in §5. It does not include actual GPU deployment or performance approval.

### Selection contract and scope of use

The current event worker calls `Scheduler::prepare_plan_with_limits`. Policy state is committed only after a verified native issue is accepted,
so rejections and cancelled preparations do not consume the fairness order.
The existing KV/flight/ledger approval path, decode outstanding≤1, and per-node serial native calls are kept.

| Environment variable at agent start | Meaning / default |
| --- | --- |
| `P4_STAGED_DECODE_MEMBERS` | Cap on decode requests per batch / 0 (no limit on this axis) |
| `P4_STAGED_PREFILL_MEMBERS` | Cap on prefill requests per batch / 0 |
| `P4_STAGED_PREFILL_ROWS` | Cap on total prefill rows per batch / 0 |
| `P4_STAGED_PREFILL_ROWS_PER_REQUEST` | Cap on prefill rows issued from one request / 0 |

If all are 0, the existing selection path is used unchanged. If any is set, the new selection applies to ordinary attention only.
If atomic verify/replay is pending or the model is equal-sequence, the existing selection is used and the diagnostics record whether the new one applied.
The values are selection caps, not memory reservations or credit. They do not raise the resident/open/fragment caps or the global byte cap.
An invalid numeric string reads as 0, as in the existing configuration scheme, so check the effective values in the artifact.

For example, the discriminating candidate for resident16, `(decode_members=4, prefill_members=4, prefill_rows=128,
prefill_rows_per_request=64)`, does not consume all 16 decodes or all 16 long prefills at once.
This is not an optimal value or a real-hardware recommendation; it is an experimental candidate within the current budget. The coalescing/open settings are sealed with it.

The per-phase sequence ID resume position is preserved, so the next request is not skipped even when the length of the eligible vector changes.
For prefill, round-robin allocation among the selected requests and the total and per-request caps apply. With capacity>1, at least 1 row of opportunity
is left for waiting prefills; with capacity=1, prefill gets an opportunity after 8 sustained decodes.
This is **starvation prevention based on accepted selection opportunities**. Time-based aging, cumulative cost deficit, and native cost prediction are not implemented yet.

### Observation contract

`BatchObservation.scheduling` holds, at selection time, the effective settings, whether the new selection applied, the open count, the admission-wait count, the outstanding-blocked count,
the missing-input count, and eligible requests per phase. It is a node-wide aggregate, not a per-request stall trace or a confirmed cause of GPU idleness.
A field missing from an older producer is `None` and is not interpreted as a measured 0. It cannot yet capture the cause of intervals in which no issue occurred at all.
A strict older consumer may reject the new fields, so the producer agent and event-drive must be deployed bound to the same change.

`RequestArtifact.output_received_ms` is the OUTPUT receive time on the run's monotonic clock and includes the terminal.
The time is captured before parsing/approval and is appended only for OUTPUTs that pass all checks. Even in a failed partial artifact it is
preserved with the same length and order as outcomes. Do not confuse it with input tokenization or admission wait.

### Actual consumption tests and verdict scope

One of the 6 `bounded_strategy_*` tests uses the real `Worker::run` thread, the event/Frame codec, and the flight/settlement/release path.
Only native is an independent stand-in. With 3 stages/8 requests, it creates 4 issues before the tail returns and checks every output position/content and per-stage KV release.
The other tests check four groups for 16 decodes, four groups for 16 long prefills (without widening the fragment), mixed quantum,
changes in the eligible set, capacity1 starvation prevention, policy invariance for cancelled plans, and preservation of the atomic/equal paths.

The new scheduling fields are compared in full against an oracle that independently collects request state before the actual native call.
Past golden JSON was not changed. The new diagnostic fields were classified into the existing cross-run pacing exclusion list,
and the ownership, membership, row, settlement, and output comparisons are kept as they are. The OUTPUT receive time is checked, on the real driver consumption path,
under three counterexamples — connection cut, deadline, invalid follow-up event — for length, order, first/last time, and partial preservation.

### Basis and scope of the policy

[llama.cpp update_slots](https://github.com/ggml-org/llama.cpp/blob/451b89bae0c4b1dd612eb503ceace906c01ddcc9/tools/server/server-context.cpp)
first builds the generating slots and, under continuous batching, processes prompts with the remaining rows.
[vLLM V1 scheduler](https://github.com/vllm-project/vllm/blob/5c642796e871e41ae75be0b402a8eaa44ee771b1/vllm/v1/core/sched/scheduler.py)
ties the actual token budget to KV allocation and sets a long-prefill limit.
[SGLang PrefillAdder](https://github.com/sgl-project/sglang/blob/a713349faf748b854ec30895abee7fd26789c6d9/python/sglang/srt/managers/schedule_policy.py)
deducts mixed decode from the chunk budget and checks KV/page boundaries.
[Sarathi-Serve](https://arxiv.org/html/2403.02310v1) covers the throughput/latency trade-off of mixing chunked prefill
and decode. These principles do not prove the optimal width or pipeline window for a specific P4 model.

P4 currently does not call the upstream server's slot scheduler. An adapter-owned `PipelinePolicy` was placed in front of the existing ordinary scheduler's
decode reservation, rotation fairness, and prepare/validate/commit path.
It derives the per-phase cap on participating requests as `ceil(eligible / (window - open))`, and if an existing explicit limit
is smaller, it honors that. With 16 long prompts, window8, and batch512, it keeps fragment1 and
prepares 8 independent groups of 2 requests × 256 rows. This fixes the earlier pure-prefill counterexample, in which every request put 32 rows into one batch and
then waited a full round. The total row count and the number of participating requests are not to be confused.

If any request is in the decode state, even if its token is currently in flight, the total prefill rows are limited to
`P4_STAGED_MIXED_PREFILL_ROWS` (starting experimental value 128). The actual ready decodes are reserved by the existing scheduler.
This is a static workload limit on a non-preemptive call, not a cost prediction or a real-time latency guarantee.
It applies only when `P4_STAGED_PIPELINE_BATCHING=1`, and the actual admission path requires a finite open window, a positive quantum, and fragment1.
It targets ordinary attention; recurrent/equal and VERIFY/REPLAY stay on the existing path.
The new policy does not claim to reserve B3/edge/receiver/broker receipts, which lie outside the request storage reservation.

### Remaining costs of this policy

**Row width, participating request count, and flight target must be chosen separately.** MI head native calls rose from 3790 to 28279.
Head RPC for 2-row decode averaged 26.24ms, versus 58.43ms for the baseline's 16-row decode. This does not mean small groups are cheaper per token.
The prefix, concurrency, and request decline differ across the observed intervals, so these means are not used as a fixed-cost regression or a precise matched kernel comparison.
Once enough independent flights are secured to fill the pipeline, it may be better to merge more decodes within the latency budget.
The current policy's `ceil(eligible/(window-open))` is a first safe choice, not a cost optimization.

**A static 128 rows is not a latency guarantee.** In the Hy3 candidate's mixed 129-row batch, of the 2692.40ms head RPC, native decode was 2685.29ms,
encode 0.72ms, and the unclassified remainder outside was 6.16ms. The order and row counts of all 19215 head traces and 19215 artifact spans were checked.
native decode includes CPU/GPU/internal synchronization. This observation says the next attribution is needed inside native;
it is not grounds to think that removing the 1ms retry or the RPC wrapper would make 2.69 seconds disappear. In the partial baseline group, native 471/span 470
did not fully correspond, so `head-cost.py` refused the detailed cost mapping.
When several non-preemptive prefills sit ahead of decode, generation wait accumulates even if each chunk is limited.

**The same number of layers does not mean the same service time.** Mean per-stage RPC for the Hy3 candidate's pure-prefill was M42 S0/S1 5.38/5.54s,
Spark 0.978s, Mac 0.331s, local 2.910s, and Ubuntu 1.383s. The overall RPC active ratio of the two M42 stages was 92.5/95.6%.
With the current cut, which has CPU expert offload and shared host CPU/DRAM, putting more work on fast devices may only lengthen the queue ahead of the slow stage.
CPU and GPU bottlenecks were not individually confirmed, but the service time imbalance was observed.
The local 3090, which secures KV first, uses about 34.8GiB of CPU weights because of 14.0625GiB of KV and about 3.567GiB of compute.
Planning must distinguish the maximum context/resident guarantee from the actual KV pool. We do not quietly shrink it to raise the GPU weight share.

**Prefill width must not be judged by the number of ready requests.** The current min gate in `drive.rs` uses the request count from
`ready_row_count()`. Under MI min4, even when the last 2 long prompts could fill 512 rows, it waits for other requests to return.
This is a counterexample showing that pure-prefill row sufficiency must be separated from the minimum request count/wait expiry for decode coalescing.
fragment1 fills the pipeline only when there are enough independent requests. Leading fragments of a single 100k request are not handled yet.
Input accounting was fixed, but MI agent RSS remained at about 35.67GiB (baseline) / 30.88GiB (candidate) even after UNLOAD.
This does not mean a heap/receipt cause is confirmed, and the B2/B3/return and broker byte lifetime gates remain open.

### Contract for the next implementation and discriminating tests

The current work order is owned by roadmap §0.V1.1. The follow-up design these results justify is:

1. **Resource lifetime and wait instrumentation:** bind actual actor enqueue→dequeue, head monotonic issue→settle,
   reasons for not issuing, active/retired receipt bytes, and B2/B3 return reservations. Break down native CPU/GPU/transfer.
   Distinguish active slot removal from final payload retirement, and pass consumption tests and mutations for normal/cancel/replay/unknown-outcome cases.
2. **Per-phase width, grouping, and window:** apply an efficient row width and independent request groups to prefill, and coalescing within a deadline
   to decode. The hard open8 is a cap, not a target to always create 8. Use the queue-free path latency divided by the slowest stage's
   service interval as the initial estimate of the needed flights, but limit it by byte/KV/request dependency.
   Feedback that widens the window further because queue-inclusive RTT grew is forbidden. The min gate is also split per phase.
3. **Cumulative prefill time budget:** predict cost per model/backend/stage/phase/row count/participating requests/KV prefix.
   When a new prefill is added, compute, for each stage the decode will pass through, the existing wait, the non-preemptive remaining execution, and the added chunk cost.
   If that expected completion time exceeds the decode's remaining latency budget, shrink or defer the prefill. Apply deficit/aging to P requests
   to prevent starvation. If a single non-preemptive call itself exceeds the target, the scheduler alone cannot guarantee that latency.
4. **KV-first cut/offloading replanning:** within the weights+KV+compute+margin and host RAM/CPU/DRAM budgets,
   verify a cut that shrinks the slowest stage via PLAN→actual peak memory→identical load. Using Spark/Mac headroom is a separate experiment axis.
   The admission promise of 100k × concurrency is kept. Simple layer-proportional estimates are not used as memory approval.
5. **Actual 100k and few requests:** first fix the policy with enough requests, then compare fragment1→2→4 independently.
   First prove sequence/token-range/KV prefix ordering and duplicate/cancel/out-of-order/RELEASE/SETTLE safety.
   node execution 1 and decode outstanding 1 are kept. Separate one long request / several long requests / a long request arriving during generation / continuous arrival
   of short new requests, and verify TTFT, TPOT p95, normal completion/release, and memory stability.

At true 100k, the KV lookup range of the actual attention is also instrumented as a cost input. In the latest
[llama-kv-cache.cpp](https://github.com/ggml-org/llama.cpp/blob/451b89bae0c4b1dd612eb503ceace906c01ddcc9/src/llama-kv-cache.cpp),

Do not assume the whole pool is computed every time from the start just because the maximum context is 100k. Some sparse
flash paths of the latest HIP are not supported, but the actual selected kernel/waste in this arm was not measured. Simply turning off unified
may change the equal-stream constraints and the unequal batch contract, so it is not changed through a scheduler knob alone.

We draw on Sarathi's chunked prefill, llama.cpp's decode-first composition of remaining prompts, and vLLM/SGLang's token/KV budgets,
but P4's distributed stages additionally need independent request groups and finite flight/return authority (source links in §11).

## 13. Instrumenting the actual storage lifetime of broker exact receipts

Baseline `ea0872d5d`. §12's sealed arms and ZIP are not changed. The goal is to avoid asserting that post-UNLOAD RSS has a heap cause
and instead to confirm, through INSPECT on a running agent, the exact Event copies the broker actually retains.
The raw data is in `target/v11-receipts-20260911/`. This unit is a CPU local control path, not a GPU performance real-hardware run.

`EventLedger` keeps an independent copy of each successful dispatch in the same count window. The operational window is
262144 and was not reduced this time. `Receipt` accounts for the Event inline/buffer capacity of the actual copy.
On count eviction it moves indexed→retired, and it subtracts from allocated after the last Arc of the front ticket is gone and the Event buffer
is dropped. EventNode's reserved completion path uses the same ledger. The snapshot is O(1) and
does not copy or serialize the original. Original delivery allocation, full equality, sequence judgement, and eviction timing are unchanged.

In an actual agent INSPECT, `broker.receipts` returns current/max bytes, cumulative commit/eviction/free, and index capacity.
Index/Arc/receipt bookkeeping, the allocator, destination copies, native, and RSS are outside the Event byte figures.
indexed/retired are not request or KV execution stages. Numeric overflow or unmeasured values are null, and failures are not shown as 0.
It includes INSPECT's own receive receipt and precedes including the dispatch of its response. The detailed contract is owned by
the [neutral Event convention](../../../../../../../../docs/event-protocol-v2.md#agent-inspection).

### Counterexamples, actual consumption, and verification

- `inspection_counts_retained_receipts_through_the_actual_control_loop`: consumes the actual broker→agent control loop→
  OUTER reply. It first takes a 4096B Event out at the destination, drops it, and sends INSPECT. The old code
  had no broker field, so it failed 1 test with `Null != 2` (exit101). After the fix it checks the actual cost of the two receipts and the 4098B payload.
- `receipt_memory_measures_independent_copies_on_both_dispatch_paths`: checks normal/reserved dispatch, four opaque
  EventClasses, moving an original with spare capacity, the exact cost of an independent copy, and conflict and exact duplicate after tampering at the destination.
- `receipt_memory_retired_bytes_survive_until_the_last_real_front_ticket`: after an actual count eviction, confirms that
  bytes remain even when one of two pinned tickets is consumed, and decrease only after the last conflict judgement.
- `receipt_memory_refusal_and_cancel_do_not_consume_storage_or_identity`: checks memory/identity preservation for return of the original allocation on Full,
  reservation cancellation, and retry with the same ID.
- `receipt_memory_tracks_actual_window_rotation_without_retaining_evicted_values`: with queue1/window8,
  delivers 128 opaque 64KiB Events alternating between the normal and reserved paths. Each time it verifies index, retained bytes, max, retirement, and freed amount.

## 17. Multiple long-prefill requests: a batching policy derived from observation

This section is a design conclusion from comparing §12's measurements with the current scheduler/drive. It is not a record of implementing or passing real-hardware runs for a new cost policy.
Execution order is owned by roadmap §0.V1.1. The comparison runs used actual inputs of at most 10.6k and are not extended to 100k verification.

### Separate the three decisions

The current `scheduler/pipeline.rs::PipelinePolicy::select` divides the number of eligible requests by the number of remaining flight slots.
This is a fix that creates independent groups; it takes no GPU cost, prefix length, stage backlog, or request deadline as input.
The per-phase issue and 2ms decode coalescer in `drive.rs` do not replace a full time-based prefill policy either.

| Decision | Purpose and direction of change |
| --- | --- |
| Batch prefill row width | Secure efficiency per native call. Pure-prefill uses a width large enough that the efficiency curve flattens; mixed batches choose under the decode completion-time constraint |
| Requests per batch | Split so that one batch does not make every independent request outstanding. Preserve the service share of requests that have waited long |
| Pipeline flight target | Secure enough that supply to the bottleneck stage does not stop. If it only lengthens the queue ahead of an already busy stage, delay further issues |

With 16 requests/fragment1/8 flights, `16×32=512` leaves no next request group, but `2×256=512`
creates 8 distinct groups. Pipeline depth can be gained without shrinking the row width. MI's head RPC did not get faster
(193→203ms) while the return wait dropped from 1948 to 196ms, which is consistent with this dependency change.
However, the overall candidate also changed the mixed quantum, so the overall 70.83% TPS gain is not decomposed into the effect of cohorts alone.

When there are enough independent requests, keep fragment1 first. When only 1–2 long requests remain, the maximum number of independent
flights also shrinks. Only then is the next prefill fragment of the same request considered. Even though the tokens are known,
each stage needs its previous prefix KV to complete and token-range ordering. decode needs the previously sampled token, so
outstanding1 per request is kept. The current pipeline policy explicitly refuses multi-fragment.

### Evolve the row limit into a cumulative service-time limit

In prefill-only intervals, large chunks reduce the number of native calls. In intervals where decode coexists, the prefill already placed on the path the next
decode will traverse must also be counted. Even if ready decodes are momentarily 0, if an earlier decode is
in flight, the decode that will arrive again must be considered. A native call, once executing, cannot be preempted under this policy.

The cost inputs inside the adapter are stage/backend/weight placement/host CPU budget, prefill and decode row counts, participating requests,
per-request KV prefix, and the actual attention n_kv/QK shape and kernel. Even for the same 128 rows, the cost with a 10k prefix and a 100k prefix
cannot be assumed equal. The effective query-key pairs of dense causal attention are roughly `q*L + q*(q+1)/2`, but
this describes the structure of the effective attention work; it is not a formula for actual kernel time that accounts for masked blocks, padding, the unified pool, MoE, or CPU offload.
Cost for new lengths/backends is measured directly and the prediction error is recorded.

In a simple model where independent stages each process same-size batches one at a time at constant cost,
`max batch/s ≈ 1/max(stage service time)`. The queue-free path latency divided by this issue interval
is used only as an initial estimate of the needed flight count. In reality, shared GPU/CPU/DRAM and edge resources also constrain it.
Increasing flights because RTT grew due to queueing makes congestion worse, so the window is not adapted this way.

The expected finish time of candidate batch b at stage s applies the following ordering constraints.

```text
finish[b,s] = max(arrival[b,s], finish[previously reserved work,s]) + predicted_service[b,s]
arrival[b,s+1] = finish[b,s] + predicted_transfer[b,s]
```

First account for the remaining time of running work and batches already issued, then check whether, with the candidate prefill added, each decode's
expected completion time exceeds the latency target. If it does, shrink the chunk or defer this prefill.
This is a policy that predicts ordering at the head, not instrumentation that subtracts wall clocks across nodes directly. It does not reverse input/KV ordering or
membership already issued. Because of prediction error and the minimum native call latency, it is not a hard real-time guarantee.

The behavior is composed as follows.

1. Only requests allowed by resource reservation, KV prefix, and dependencies are candidates.
2. Select decode groups close to expiry, but do not serialize by gathering all independent decodes into one group.
3. Select prefill requests by cumulative unserved amount and wait time. Fairness is charged not only in rows but in units of expected bottleneck service time,
   and corrected with actual cost. A rejected plan does not consume share.
4. Place discrete chunk candidates virtually behind each stage's existing work and compare decode completion times and prefill throughput.
   Among widths large enough to improve native call efficiency, choose a candidate that satisfies the latency and memory budgets.
5. Secure flights, edge/receiver bytes, KV, and mandatory return reservations together, then finalize the ledger and membership.
   On completion, feed back the actual cost and prediction error and update the next selection.

Permanent decode priority starves prefill, and enforcing only prefill's minimum service share can exceed the decode target under overload.
So bounded aging/service share and admission are used together. When sustained arrivals exceed the bottleneck's processing
capacity, finite memory and finite wait for every request cannot both be guaranteed, so admission wait/rejection is
made explicit. This is not hidden by quietly shortening long inputs or lowering the resident promise.

This direction uses the chunked prefill and latency-bounded mixed batching of [Sarathi-Serve](https://arxiv.org/abs/2403.02310) and
the decode-first / remaining token budget principle of [vLLM's chunked prefill](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill).
Not carrying a single executor's full decode selection over to P4 as is, and adding
independent request groups, cumulative per-stage service, and finite flights, is a design judgement based on this code and these measurements.

### Selection specification by execution state (analysis 2026-09-12, not implemented)

The efficient row width is not assumed to equal the maximum UBATCH. For the same backend/batch assignment and prefix range, find the width at which
per-row native cost and bottleneck throughput improve, and keep that width within the latency constraints.
The following table is a decision specification derived from the §20 comparison; it is not performance approval or a completion record for a new algorithm.

| Current state | Action to choose | Outcome to avoid |
| --- | --- | --- |
| Many long prefills, no decode | Keep a large row width, split active/ready/inflight, and issue independent request groups in rotation | Binding all requests as outstanding in one batch |
| decode coexisting with long prefill | Predict decode completion time behind already-issued work and shrink/select the prefill chunk | Rejecting the whole large chunk so that only small decodes repeat, or starving prefill |
| Bottleneck stage idle from lack of supply | Increase the supply of independent groups within the existing safe window | Raising only the head batch fill rate while emptying downstream |
| Bottleneck stage running continuously, only the queue ahead of it growing | Suppress further issues and relieve the cut/offload/shared CPU·DRAM bottleneck | Continually raising the flight target on the strength of observed RTT growth |
| 1–2 long requests, idle because of the fragment1 dependency | Overlap bounded prefill fragments after proving per-stage prefix KV completion and ordering | Removing KV ordering/cancellation checks merely because the input tokens are known |
| Insufficient KV/return reservation | Limit external waiting and make admission wait/rejection explicit | Reporting the declared resident count as actual concurrent admission, or approving sustained swap/recompute as saturation |

In a simple uniform-batch/independent-device model, the starting point for the needed flight count is
`ceil(round-trip latency excluding queue wait / batch processing interval of the bottleneck resource)`.
This value is an estimate to be corrected by measurement, not authority to raise the existing resource credit cap.
If one device hosts several stages or CPU and transfer resources are shared, the combined work on that resource is also included in the bottleneck calculation.
The selection goals are fewer bottleneck supply gaps and normal-response throughput. Maximizing batch row fill rate, open window fill rate, or fast-GPU
utilization individually can conflict with the latency/memory budgets.

### Hy3 also needs to change the work placement of its slow stages

Hy3 pure-prefill RPC is 5.38/5.54s on the two M42 stages, 0.978s on Spark, and 0.331s on Mac. While the slow stage keeps working,
the fast stages cannot be supplied more of the same work. In a simple model where the same cost repeats, Mac's
RPC duty can be 0.331/5.54≈6% while the whole pipeline is already at bottleneck capacity. This is an example that explains what the imbalance means, not a prediction of GPU utilization or
a duty computation for this whole real-hardware run. Growing queues with 100% on every device as the goal can leave throughput unchanged
while only TTFT, ITL, and retained memory grow.

So, after separating M42's CPU compute/DRAM, GPU, and synchronization costs, compare legal cuts and
weight placements that lower the cost of the slowest stage. First secure on the GPU the actual KV, compute, and margin for 100k × the guaranteed concurrency, then place
weights in the remaining capacity. Also account for the execution cost of experts placed in host RAM and CPU contention between the two stages.
Moving work to Spark/Mac is allowed only for candidates that pass the actual memory, supported kernel, and network boundary checks. Giving every stage
the same number of layers is not the goal, and allowing offload does not by itself guarantee a speedup.

### The next experiments discriminate the policy's decisions

After the return lifetime is connected, compare row width / participating requests / flights as independent axes within the same safe window. Compare the existing full selection,
the current cohorts, and the past tuned MI cap4/Hy3 cap2 with the same native, inputs, and arrival sequence. Only then turn on the cost policy.
Each arm confirms the inputs below with the actual tokenizer and preserves sufficient output together with natural EOS and content verification.

| Input/arrival condition | What to discriminate |
| --- | --- |
| Several actual 100k requests arrive at once | Does it keep a sufficient row width, reduce stage supply gaps, and shorten prefill completion time for identical inputs? |
| Several 100k requests arrive during decode | Does the cumulative prefill time limit reduce decode p95/p99 ITL and long stalls? Does prefill still progress? |
| Short requests arrive continuously while a long request is processed | Are both short-request TTFT and the long request's maximum wait bounded? |
| 1–2 actual 100k requests | Can the supply limit of fragment1 be separated from the effect of safely proven fragment2/4? |
| Sustained waves, cancellation, connection failure | Do KV/return/receipt memory stay stable, and are normal release, UNLOAD, and partial-result preservation maintained? |

Secure 100000 input tokens + an output budget, not a fixed 100k context. Distinguish the total capacity of the shared KV pool from the per-request
maximum context, and record the number of requests actually admitted concurrently. Use GPU kernel/SM and memory bandwidth instrumentation,
stage queue/native/transfer, per-request TTFT/ITL, and normal-response goodput separately. batch512/512 and
open8/8 are observations, not success conditions. If across repetitions throughput flattens while only waits grow, stop widening flights;
if native cost grows, readjust chunks/batching; if the bottleneck stage stays busy, move to the cut/offload axis.

## 19. Per-stage prefill service budget within a fixed window

Started from main/GitHub baseline `7cac79c6ab7be0c035465cd65ea739303d839dbe`. This unit is preserved separately in
`target/v11-service-budget-20260911/`. Earlier sealed material is not changed.

### Decision and scope

The existing mixed 128-row cap does not limit cumulative time. Issuing the same 128 rows many times piles non-preemptive prefill
ahead of decode on the slow stage. This first unit sends the monotonic-clock time of actual downstream Frame calls
back to the head and computes, for each stage, the expected cost of incomplete open prefills + the candidate cost.
When all costs are known and any stage exceeds the soft budget, it re-plans with ready decodes only, excluding prefill.
A rejected candidate does not commit fairness, flights, or requests. Cost samples are not KV/flight/edge return authority.

`P4_STAGED_PREFILL_SERVICE_MS` is disabled by default. It is allowed only with ordinary attention/pipeline/fragment1 and
open1–128/stage2–64, and it does not raise resident, window, or return caps. Only actual computations that include prefill
send a feedback Event. It does not add needless events for every decode-only call or push out the cost profile.
It checks source, load/session, the exact execution list and row membership, and duplicates/conflicts. It is bounded by history128/profile256
and the max of the 8 most recent costs per power-of-2 bucket of per-phase row count/request count/max position.
If samples or open membership are unknown, it marks `cold` and uses the existing bounded policy. When all earlier prefills have been
settled, it allows a `progress_probe` of one configured quantum. The full pure-prefill width is preserved.

This is a first cost policy for per-stage prefill backlog. Actual `n_kv`/mask and GPU kernel cost,
full-pipeline completion prediction including decode/transfer/non-preemptive remainders, dynamic chunk width, and per-request time deficit/aging
do not exist yet. `progress_probe` is a device to avoid permanently stalling prefill, not a time SLO.
With too few samples the gate does not act, and a small budget can reduce supply, so no performance gain or default is approved before comparing the actual cold/deferral ratios
against decode latency, prefill completion, and overall goodput.

### Counterexamples and verification method

- On a normalized 3-stage setup, refuse when an existing prefill cost of 100 plus the next 100 exceeds a budget of 150. After an actual completion sample from middle,
  the tail's incomplete 20 remains and the candidate is allowed. Check that this does not replace flight settlement.
- On an actual `Worker::run` 3-stage setup with completion queue1/open4 and 8 requests (8/96 prompts, 48 outputs), route feedback and, after an
  over-budget verdict, check that the actual native input is decode-only, plus the pure full width, the progress probe, and full settlement/release.
- After actual head Frame consumption, refuse a fake stage source, a wrong row membership, and conflicting samples. Confirm that not only the cost history but also
  open/flight/outstanding/native call counts are unchanged. An exact duplicate is not re-learned.
- After an actual idle UNLOAD, check that a late cost Event does not reopen the load/session or call native.
- An unknown 100k shape/stage/open history is cold. Even across 600 reuses, the history/profile/recent sample caps are respected.

### Cause 1 — independent prefill groups disappear on the slow path

The key is `free = window - open`, `ceil(eligible/free)` at `scheduler/pipeline.rs:44`.
With open7/window8 and 8 eligible prefills, all of them join one batch. `state.rs::phase_within` blocks
outstanding requests under fragment1. So filling 128 rows as 8 requests × 16 rows makes all 8 requests wait for the same return.
In the actual previous-placement automatic arm, 215 of the 261 mixed batches were `prefill128 + decode1, members9`.

Keeping the row cap, open, fragment, and native unchanged and changing only the explicit prefill participation cap to 2, the median mixed head RPC
did not get faster (75→80ms), but the median idle before that issue dropped from 670 to 132ms. The mean concurrency of independent prefill RPCs
went 1.210→3.672 within the prefill interval, and overall RPC went 2.687→4.658/8. The throughput and long-TTFT improvements are consistent
with the effect of supplying independent groups. Since changing the participant count also affects the backend execution shape, not every improvement rate is attributed to idleness alone.
Mixed ITL worsened from 863 to 1078ms. Supplying more independent batches and bounding generation latency are choices to be made together.

### Cause 2 — a fixed 250ms service budget has no grounds for adoption in this screening

With automatic grouping there were 32 actual defers, but TPS went 14.86→14.65 and ITL 863→866ms.
With at most 2, there were 1284 defers, TPS went 27.42→13.87, and long TTFT went 72.813→205.312s.
Compared with the drop in median ITL (1078→1027ms), the throughput loss is large, and p99 worsened from 1353.8 to 1863.16ms.
A functional proof that cost feedback works is different from a performance verdict that it is a useful scheduling policy.

The current `ServiceBudget` looks only at a cap on per-stage pending prefill + candidate and does not shrink the chunk width.
With the previous placement, mixed stage service was roughly 75–125ms, so 250ms is a tight value for sustaining several independent prefills.
A policy that emits small decode-only batches after a rejection can reduce the work supplied to the pipeline,
and it does not directly bound the decode completion time or tail latency over the whole path. These figures are grounds for not making 250ms a default or recommended value.
The experimental option stays disabled by default. The time feedback itself is not removed; it is reused for dynamic chunk/grouping/completion-time decisions.

### Cause 3 — the MI native's GPU layer computation diverged from the preserved plan

In the current native451, `src/llama-model.cpp:1507` has `i_gpu_start=max(n_layer_all+1-n_gpu_layers,0)`.
For the 45-layer model, the preserved plan used `n_gpu_layers=45-b` with b as each cut's begin, so the GPU start was b+1.
We split the actual 16 PLAN/LOAD log groups with a regular expression and confirmed that **in each of the 8 stages, its own first repeating layer was on CPU**.
Do not confuse this with whether the output layer or input embedding is on CPU. KV was being placed on the device by a separate cut and was not changed by this fix.

With the same 2-request grouping and service OFF, only the value was increased by 1 to match this native. We verified in both PLAN and actual LOAD that each cut's first repeating layer
was also assigned to ROCm0. At the same rows, context, and concurrency, TPS went 27.42→75.02,
long TTFT 72.813→22.351s, and the mean GPU sample 16.49→55.33%. This gain is not an achievement of the batching algorithm alone.
Peak VRAM was 30.91GiB on the largest device, and the KV conditions were kept within the existing 64GiB per-device budget.
The whole CPU_Mapped buffer also contains weights of the non-executing prefix, so that figure is not taken as actual CPU compute volume.

## 23. Investigating decode-first with remaining prefill, and the P4 applicability judgement (2026-09-12)

The user's question was: "shouldn't we put the small generation requests in first and fill the remaining space with the prefill to process this round?"
The conclusion is: **adopt that policy as the default direction, but limit both the remaining row space and the remaining execution time.**
P4 ordinary attention already puts generation rows first. What is missing is control of generation result latency and preservation of independent batches.
Below is an investigation that separates confirmed external implementations, current P4 facts, and proposed application. Improvement rates from external experiments are not used as P4 expectations.

### Comparison with external papers and implementations

### What current P4 lacks

The same stored artifacts were re-aggregated for this question without modification. Only **actual consecutive non-terminal
token receive intervals** of the 8 short requests are used, and intervals crossing an interval boundary are excluded. The prefill interval runs from the long wave's arrival
until the first outputs of all 8 long requests have arrived. This is not a distribution of per-request mean intervals.

| Interval within the same run | Corrected GPU placement · automatic grouping p50 / p95 (ms) | Corrected GPU placement · at most 2 per group p50 / p95 (ms) |
|---|---|---|
| Before the long requests arrive | 45 / 88.1 (320 intervals) | 46 / 94.3 (298 intervals) |
| Long-request prefill interval | 637.5 / 780 (270 intervals) | 636.5 / 776.55 (270 intervals) |
| After all long-request first outputs arrive | 76 / 112 (1167 intervals) | 76 / 110 (1185 intervals) |

In both runs, every one of the 272 mixed batches had exactly 1 generation row, and the median prefill row count was 128. Median head RPC was
9ms for decode-only and 67ms for mixed. It is directly confirmed that even with generation-first batching, generation intervals widen greatly while prefill
is processed. However, each interval's context/request population differs, so 45→637.5 is not cited as a causal multiplier of a pure chunk change.
`decode-interference.json` preserves the artifact SHAs, intervals, and per-request/pooled aggregates.

The selection raw data was also checked. In both arms, the first mixed batch had 8 eligible decodes and open0, yet selected only 1 generation
and added 128 prefill rows. The following six batches, with eligible decodes going 7→2, also selected 1 generation each.
So 7 of the 272 batches left ready generations behind, and in the other 265 there was only 1 eligible decode to begin with.
This proves the generation participation cap actually took effect, but it cannot be treated as the sole cause of the whole 637ms latency.
The first selection and the subsequent inter-phase wait/compute cost must be varied together and compared.

1. `scheduler.rs::plan_bounded_ordinary` assigns decode first and then fills prefill. However,
   because of `decode_members = ceil(ready_decode/free_flights)` in `pipeline.rs`, some ready generations are
   intentionally left for the next batch. This is a spreading policy for the pipeline, not the same contract as "all ready generations first".
   Removing that limit could bind decode requests into one flight, so both latency and independence must be compared.
2. `server_physical.cpp::handle_physical_batch` encodes and returns the whole result after each capsule's execute/sample.
   Even if decodes are at the front of the row array, the structure does not deliver their results first while prefill is computing.
   Nor can a big prefill that native is already executing be interrupted by the priority of generations to be added later.
3. `mixed_prefill_rows` is a fixed row count that ignores context position. In full causal attention, appending c tokens after existing KV of length L
   gives roughly `c*L+c*(c+1)/2` effective query/key pairs.
   So 128 rows at position 1k and 128 rows at position 96k are not the same work. SWA/MLA/recurrent must use per-model costs.
4. `service.rs` already sums the per-stage expected cost of open prefills but does not learn decode-only cost.
   It does not compute the remainder of running work, inter-stage arrivals, or the tail completion time of new decodes, and when it rejects a large candidate
   it does not look for a smaller chunk to put in instead. The degradation in the earlier 250ms arm is a counterexample to this specific policy.
5. Ordinary attention and equal-width recurrent/hybrid have different legal physical batches. In the latter, putting 1 decode row and
   a prompt into the same equal-width call can truncate the prompt to 1 row as well, so the phases are currently separated.
   The same service goal applies, but the same mixed shape is not forced on every backend.

### Policy to change

**Protect the next completion time of generation first, rather than giving generation the leftover rows.** Generation participants in the next issue
must satisfy readiness, resolved dependencies, and KV/return reservation availability. Select the generations that have waited longest first, and
compare against a direction that eliminates excluding additional generations based only on the momentary free count even though they fit in the time/physical budget.
If generation groups with different deadlines need to be split, flow them out immediately as several bounded batches. Do not create a new global barrier
that merges all generations into one and waits for that return.

Then select the prefill candidate chunk. The candidate's condition is not only the row cap but also **the expected completion time of generation requests
affected by the same batch and by already-issued batches**. The completion prediction for batch j at stage s is updated in actual queue order as
`F[j,s] = max(arrival[j,s], F[j-1,s]) + estimated_service[j,s]`, and arrival at the next stage adds
transfer. The sampler/return latency after the last stage is included too. Use each device's durations and ordered events,
and do not directly subtract unsynchronized wall clocks of different hosts. Do not reverse an already committed order.

Candidate search runs within the current safe caps. Choose the chunk with high throughput within the range that satisfies, including the error margin, a prediction that reflects
context length, P/D row counts, request count, backend, stage, and offloading state. If cost monotonicity is
confirmed, use binary search; if it is non-monotonic (e.g., kernel switches), use a verified candidate set. When data is insufficient,
use the existing conservative cap and do not label it a "deadline guarantee". Prefill 0 is allowed when needed, but
a state in which decode-only itself exceeds the target is declared an overload/placement bottleneck.

In the implementation, 0 in `OrdinaryLimits` currently means "unlimited / no separate limit", so expressing permission for prefill 0 by assigning 0
to an existing field would do the opposite. An explicit forbid/finite budget representation or exclusion of prefill demand must be used.
Also include in the prediction horizon the case where the last prompt is already in flight and its first generation will soon be ready.
Do not pile long prefills to fill the window in advance just because there are currently 0 ready decodes.

When there are several long prompts, do not put a little of each into one batch and lock all of them until the next issue. Keep independent
groups as in §22, and make the row width within each group large enough for compute efficiency. At the same time, select the next group by each prompt's cumulative service
shortfall and wait time. Use predicted/measured cost units rather than simple token fairness.
If new-request admission persistently exceeds throughput, decode latency and prefill non-starvation cannot both be guaranteed, so
admission wait, memory/return reservation, and the overload verdict are bound together.

**The target of "saturation" is the bottleneck device's effective capacity, not a batch's row cap.** If the queue-free round-trip time of same-size batches
is R and the bottleneck stage service is S, `ceil(R/S)` is a starting point for estimating the needed number of independent flights.
This is a uniform steady-state approximation, not a control law that raises the cap indefinitely using an R that includes observed queue wait.
Verify within the existing window allowed by requests, KV, and bytes, and if the bottleneck is already busy, reduce queue latency instead of adding flights.

When Hy3's slow CPU expert stage keeps working while the other GPUs wait, the batcher alone cannot bring every device to
maximum utilization. Reserve KV in GPU memory first, subtract compute/flight headroom, then place weights,
but adjust the cut and CPU/device assignment based on each stage's actual time. Mac unified memory's RAM and
VRAM are not added up as separate physical capacities. The fragment1 dependency of one or two 100k prompts is a separate cap, and
multiple fragments of the same request are allowed only after proving prefix-KV ordering, cancellation, and return.

### Discrimination criteria for the next experiments

1. First obtain decode-only and prefill-only service curves with the same model, device placement, sources/binaries, and inputs.
   Distinguish the start, middle, and near-96k regions of the context, and measure the repeated KV/issue cost of small chunks and the latency of large chunks.
2. Inject long prompts into requests that are already generating. Compare the current policy, a change to the generation participation limit, and time-fitted chunks,
   one change at a time. Use actual per-token p95/p99 intervals and ready→issue→tail completion.
   A result where decode got faster only because prefill almost stopped is not approved as an overall improvement.
3. Under simultaneous arrival of many long prompts, measure the number of independent flights, stage idle reasons, prefill tokens/s, TTFT, and each request's
   service intervals. Compare within the same safe window, and report batch width, flight count, and GPU busy separately.
4. With actual 100k inputs, sufficient natural output, and continuous waves, check acceptance of content/length instructions and full completion, release, and UNLOAD.
   This is not substituted by the mere fact that the context setting is 100k or that a 4255-token input passed.
5. Repeat the same conditions and separate the effects of hardware placement fixes from scheduler fixes. Do not extend MI250 single-server results
   to approval of Hy3 on multiple physical hosts. State the GPU analysis intervals, TPS denominators, and truncated/below-quality responses explicitly.

The sole owner of the implementation order that follows from this investigation is roadmap §0.V1.1. §22 is the first independence unit;

### Comparing not only the paper text but the executor's semantics

[Sarathi-Serve §4.3](https://arxiv.org/html/2403.02310v1#S4.SS3) sets the allowed token budget from a one-time profile, weighing the service TBT target and chunk cost
together. §4.2 orders ongoing generation → ongoing P → new requests.
This is a principle of binding batch composition to a service target, not an instruction to copy a specific model's 256/512 tokens into P4.
We re-compared vLLM's [chunked-prefill description](https://docs.vllm.ai/en/stable/configuration/optimization/#chunked-prefill) and
TensorRT-LLM's [IFB/scheduling](https://nvidia.github.io/TensorRT-LLM/1.3.0rc15/features/paged-attention-ifb-scheduler.html).
The P/D ordering within the input tensor and request priority are different contracts.

This time, the official [Sarathi source](https://github.com/microsoft/sarathi-serve/tree/96f9911790ecc00af12ee9fae47cb8fa9ba0d199) was
pinned at `96f9911790ecc00af12ee9fae47cb8fa9ba0d199` and the following were read directly.

| File | Behavior confirmed |
|---|---|
| `sarathi/core/scheduler/sarathi_scheduler.py` | Skips sequences currently running in this selection and assigns paused generations first. Assigns `chunk_size-num_batched_tokens` to ongoing prefill, then admits new requests. States explicitly that request group composition can differ under PP |
| `sarathi/core/scheduler/base_scheduler.py` | Limits the number of running batches to the PP size and returns one on step completion. Does not use the return of one batch as completion of all pipeline work |

### What to drop from the existing candidates, and the final selection rule

The cost feedback from c6bd6c597 can be used as observational data, but its cold/rechunk gate is not made the default
controller of the operational candidate. Issuing actual requests 1 row at a time because there is no initial measurement, or continually learning the maximum of all past costs
from customer requests, has already been observed to risk reproducing the §26 regression.
This time the order is **cost profile first → fix operational values for the two objectives → seal source/profile → main test without changes**.

The P4 application is: independent generation/P groups within the existing finite window + priority assignment of the selected generations + remaining P within the total token budget.
The existing fairness rotation, minimum prompt progress opportunity, and KV/flight/settlement authority are kept. GPU fill rate alone is not used as the objective function.
Initial short P groups keep pure P supply until actual generation starts, so they are not chopped up merely because future generation is flagged.
The base cost model for policy selection is the per-stage measured `L=sum(t_s)`, `S=max(t_s)` and the capacity of a finite number of independent groups M,
`b*min(M/L,1/S)`. This formula is a model for narrowing profile candidates and does not prove communication/shared device/actual service performance.
Row width, group count, and token budget are each decided, and configurations not measured on the target model/context are not approved as fastest.

The advance cost samples bind together the P/D row counts of actual physical batches, full request positions, and each stage's RPC/queue/transfer.
Splitting context ranges by prefill position alone would miss the long KV of D in the same batch, so it is not allowed.
Initial cold LOAD/graph preparation cost is not mixed into steady-state cost; it is reported separately under first-request latency.
After the main test, we do not pick a more favorable chunk or acceptance threshold and run again. Safety fixes for run failures are kept distinct from performance exploration.

The screened policies are two: throughput-first and latency-first. Both use the same safety/quality contract. The latency targets are
declared in advance as MI250 actual ITL p95 250ms and Hy3 5000ms, and the most efficient token budget within that constraint is chosen.
If the target is found unattainable, it is not raised to force a pass. For throughput-first, the latency/long-TTFT loss is reported as is.
Cost and memory for actual 100k/long responses are a separate real-hardware target and are not approved from the 4k profile alone.

Turn 1 (this one) is the fixed point for this design. The next 2 turns are used only for implementation/verification and real-hardware wrap-up. Sources, profiles, responses, verdicts,
executable hashes, and cleanup are preserved, the work ends at turn 3, and no further research or next candidate is started automatically.

### Algorithm verdict and bounded work for the next version

The user's proposal, 'put ready decodes in first and use the remaining budget for chunked prefill', is the adopted composition principle.
However, the remaining budget is not the whole physical UBATCH but a total D+P budget pre-measured for that model, device, and context
to fit the latency/throughput objective. The pipeline is supplied with these small batches as several independent request groups.
The current results do not negate the generation-first principle; they are evidence that three layers must be handled together.

1. **Request selection:** ready D first, P in the remaining budget, and rotation/starvation prevention that gives long requests a chance to progress.
   The generation input dependency is kept with outstanding1 per request, and completion of existing work is not made a global drain condition.
2. **Pipeline supply:** keep independent groups according to the admitted generation population. Do not merge all ready requests into
   one big batch, and limit the coalescing target to at most the group width that can currently be legally formed.
3. **Backend cost:** token count alone does not bound context and KV mask cost. Even for the same 512 rows, head native was observed at about 0.18→0.42→0.58s
   on the way into 100k. This is an observation within the same arm,
   not a causal decomposition into a single cost factor. It is to be cross-checked further with the raw data of completed arms.

The next version does not start with exploring new knobs. The first task is to build a proper cancel/drain/RELEASE path for timeouts
so that owners/frontiers and all reservations are returned without forced native termination, pinned by actual consumption/mutation tests.
Next, on the same long context, record separately the actual n_kv, the effective per-request KV range, CPU mask build/copy, and
HIP attention time. If waste from the shared range is confirmed, fix the mask/working set inside the native/llama isolation boundary,
