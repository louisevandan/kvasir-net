## 2. MI250: 직렬화 관측은 유지, open-batch 상한 인과는 미확정

모델은 두 실행 모두 Step-3.7-Flash-Q4_K_XL, 45층이다. 아래 TPS는 artifact의
생성 토큰 합계 / `elapsed_ms`이며 적재 성능·정상 응답으로 승인한 유효 TPS가 아니다.

| 조건 | 8-stage / 한 머신 | 16-stage / 두 머신 |
| --- | --- | --- |
| resident / 요청 수 | 256 / 256 | 16 / 16 |
| 요청별 context 상한 | 512 | 100512 |
| 실제 입력 | 총 10160토큰, 요청당 평균 39.7 | 100000토큰 1건 + 61토큰 15건 |
| 출력 상한 / 종료 | 64 / 전부 length | 512 / ignore_eos=true, 전부 length |
| batch / ubatch | 512 / 512 | 512 / 512 |
| 완료 / 해제 | 256 / 256 | 16 / 16 |
| 생성 토큰 / 시간 | 16384 / 54.318s | 8192 / 1072.206s |
| generated TPS | 301.63 | 7.64 |
| 요청 묶음 | 32요청씩 서로 다른 8개 묶음 | 513개 배치는 16요청, 이후 201개는 1요청 |
| idle_gated 합계 | 0 | 0 |

따라서 **301.63 → 7.64를 노드 수 증가의 손실률로 계산할 수 없다.** resident, 입력 길이,
출력 길이, EOS 조건, KV 크기가 함께 바뀌었다. 16건 모두 실제 100k prefill한 실행도 아니다.

16-stage의 전형적 배치는 `497 prefill + 15 decode`(200회)다. 같은 요청의 decode는
이전 토큰 반환 전 발행할 수 없고, 기본 prefill fragment 창도 1이다. 한 배치가 16요청을
모두 점유하면 다음에 발행할 독립 요청이 없어진다. 8-stage의 32요청 묶음 8개와 대조된다.
이는 **요청을 한 묶음에 소진하는 정책과 요청 의존성의 결합**을 우선 검사할 근거다.

원본 `stage-overlap-diagnosis.json`의 평균 0.8618/16, 단일 활성 86.1576%는
호스트별 Unix 시각을 보정 없이 합친 **RPC 구간**이다. GPU 계산 겹침이나 정확한 전역 비행 수가 아니다.
시계를 섞지 않고 머신별 8개 stage를 재집계하면 다음과 같다.

| 머신 | 자체 분석창 | 평균 동시 RPC | 최대 동시 RPC |
| --- | --- | --- | --- |
| MI250-01 | 1071.329s | 0.42535 | 1 |
| MI250-02 | 1065.803s | 0.43877 | 1 |
| 8-stage 비교 실행의 한 머신 | 54.172s | 5.84174 | 8 |

각 머신 내부 직렬화는 이 재계산으로도 유지된다. 다만 현재 `max_open_batches` 기본값은
0(상한 비활성)이며 실제 프로세스의 유효 환경변수는 자료에 봉인되지 않았다.
gate 거절 0과 함께 보면 **open-batch 설정이 차단 원인이라는 선언은 보류**해야 한다.
현재 event adapter에서 `queue.is_running()` 호출도 찾지 못했다. 이름만으로 제거할 대상이 아니다.

머신 간 7→8의 관측 간격 평균은 19.3515ms다. 미보정 전체 batch 지연 1491.438ms와 단순 비교해도
약 1.30%다. 이 값에는 시계 오차·큐·전달이 섞인다. ping RTT나 baseline 차감으로
“실제 네트워크 비용 1% 미만”을 확정하지 않는다. 다른 사용자 부하가 있었던 MI250-01의 GPU 표본도 분리해야 한다.

| 16요청 혼합 arm | batch / ubatch | generated TPS | 100k 요청 TTFT |
| --- | --- | --- | --- |
| 기준 | 512 / 512 | 7.640 | 843.442s |
| 논리 폭 증가 | 2048 / 512 | 6.718 | 972.188s |
| 논리·물리 폭 증가 | 2048 / 2048 | 5.348 | 1269.162s |

각각 단회다. 마지막 비교는 UBATCH 하나만 바꾼 실험이 아니다. 큰 폭이 최선이라는 근거는 없지만
이 세 점으로 최적 폭도 정할 수 없다. 모든 출력이 length이고 사실을 지어낸 응답도 있어 서비스 품질 승인은 없다.
기존 MI250 artifact에는 `output_received_ms`가 없어 실제 토큰 간격 분포도 재구성할 수 없다.

## 3. Hy3: 긴 prefill의 지연 전파와 보관 메모리

Hy3 Q5_K_S 191.884GiB, 80층, 5호스트/6stage다. M42의 3090 두 장, Spark,
Mac Metal, 로컬 3090, Ubuntu 2070에 걸쳤으며 CPU expert 오프로딩을 포함했다.
resident 8, 요청별 context 102400, batch/ubatch 512/256, open-batch 8, fragment 1.
실제 입력 길이 31643/63682/91696, 두 웨이브 총 16건/966748토큰, 출력 상한 8192였다.
6시간 deadline에 16건 전달, 4건 완료·해제, 12건 미완료, OUTPUT 16438건으로 실패했다.
완료 4건도 산술 검사는 통과했지만 서술 품질/분량 조건은 실패해 유효 TPS 승인은 없다.

| 파생 관측 | 결과 / 해석 |
| --- | --- |
| 같은 요청 연속 OUTPUT 간격 | 16430쌍을 decode 입력 위치와 연결, 미연결 0 |
| 초기 prefill 혼합 구간 | 간격 중앙 29.790s; head issue 창 186.65분 |
| decode-only 구간 | 간격 중앙 1.869s; head issue 창 53.60분 |
| 후기 prefill 구간 | 간격 중앙 31.150s; head issue 창 119.65분 |
| decode-only batch인데 20초 이상 출력 공백 | 1963건 모두 이전/현재 head issue 사이에 prefill 포함 batch 존재 |
| 동일 91696토큰 입력의 편차 | 요청 3: prefill 428회, TTFT 186.46분; 요청 6: 240회, TTFT 92.91분 |
| 최초 stage prefill 비용 | native execute 평균 6872.08ms / RPC 평균 6899.91ms; parse 0.734, match 0.484, encode 5.387ms |
| decode 묶음 | 대부분 3요청/5요청 두 묶음. resident 8로 decode 256행 채움은 불가능 |

시간창과 표본 수가 다른 통계를 나눠 TPS를 만들지 않는다. native execute에는 CPU/GPU/전송이
섞여 있어 커널 계산 비용으로 부르지 않는다. prefill은 M42, decode는 Spark의 RPC가 가장 길었다.
tail 한 단계나 배치 행 수만으로 전체 비용을 예측하기 어렵다.

첫 stage가 발행한 payload 합은 10908855372B(10.15966GiB)다. 입·출력 full payload를
두 번 보관하면 약 20.3193GiB이고 Spark agent 최종 RSS는 약 20.546GiB였다.
broker의 full-event receipt 보관과 일치하는 강한 후보이나 heap 귀속을 입증한 값은 아니다.
**활성 flight 제한과 이미 끝난 receipt의 보관 제한은 별도 예산**이어야 한다.

## 6. 후속 구현 — bounded ordinary 선택 후보 (2026-09-11)

계획 커밋 `974350c27`은 GitHub `main`에 push 확인 후 구현을 시작했다.
아래는 §5의 문서 전용 변경 뒤에 수행한 별도 작업이다. 실제 GPU 배포/성능 승인은 포함하지 않는다.

### 선택 계약과 사용 범위

현재 event worker가 `Scheduler::prepare_plan_with_limits`를 호출한다. 검증된 native issue 수락 뒤에만
policy state를 commit하므로 거부/준비 취소로 공정성 순서를 소비하지 않는다.
기존 KV/flight/원장 승인 경로, decode outstanding≤1, node별 native 호출 직렬성은 유지한다.

| agent 시작 시 환경변수 | 의미 / 기본값 |
| --- | --- |
| `P4_STAGED_DECODE_MEMBERS` | 한 배치의 decode 요청 수 상한 / 0(축 제한 없음) |
| `P4_STAGED_PREFILL_MEMBERS` | 한 배치의 prefill 요청 수 상한 / 0 |
| `P4_STAGED_PREFILL_ROWS` | 한 배치의 prefill 총 행 상한 / 0 |
| `P4_STAGED_PREFILL_ROWS_PER_REQUEST` | 한 요청에서 발행할 prefill 행 상한 / 0 |

모두 0이면 기존 선택 경로를 그대로 사용한다. 하나라도 설정하면 ordinary attention에만 새 선택을 적용한다.
atomic verify/replay가 대기 중이거나 equal-sequence 모델이면 기존 선택을 사용하고 진단에 적용 여부를 남긴다.
값은 선택 상한이며 메모리 예약/credit이 아니다. resident/open/fragment 상한이나 전역 byte 상한을 올리지 않는다.
유효하지 않은 숫자 문자열은 기존 환경설정 방식과 같이 0으로 읽히므로 artifact의 유효값을 확인한다.

예를 들어 resident16의 판별 후보 `(decode_members=4, prefill_members=4, prefill_rows=128,
prefill_rows_per_request=64)`는 16 decode 또는 16 장기 prefill을 한 번에 모두 소비하지 않는다.
이는 최적값/실기 권장값이 아니며, 현재 예산 범위의 실험 후보다. coalescing/open 설정도 함께 봉인한다.

phase별 sequence ID 재개 위치를 보존해 eligible 벡터 길이가 변해도 다음 요청을 건너뛰지 않는다.
prefill에는 선택된 요청 사이의 순환 배분과 총량/요청별 상한을 적용한다. capacity>1이면 대기 prefill에
최소 1행의 기회를 남기고, capacity=1에서는 지속 decode 8회 후 prefill 기회를 부여한다.
이것은 **수락된 선택 기회 기준의 기아 방지**다. 시간 기반 aging·누적 비용 deficit·native 비용 예측은 아직 구현하지 않았다.

### 관측 계약

`BatchObservation.scheduling`은 선택 시점의 유효 설정·적용 여부·open 수·수용 대기 수·outstanding 차단 수·
입력 부재 수·phase별 eligible 요청 수를 보관한다. node 전체 집계이며 요청별 stall trace나 GPU 유휴 원인 확정값이 아니다.

### 정책의 근거와 적용 범위

[llama.cpp update_slots](https://github.com/ggml-org/llama.cpp/blob/451b89bae0c4b1dd612eb503ceace906c01ddcc9/tools/server/server-context.cpp)는
생성 슬롯을 먼저 구성하고 continuous batching일 때 남은 행으로 prompt를 처리한다.
[vLLM V1 scheduler](https://github.com/vllm-project/vllm/blob/5c642796e871e41ae75be0b402a8eaa44ee771b1/vllm/v1/core/sched/scheduler.py)는
실제 token budget과 KV 할당을 연결하며 long-prefill 한도를 둔다.
[SGLang PrefillAdder](https://github.com/sgl-project/sglang/blob/a713349faf748b854ec30895abee7fd26789c6d9/python/sglang/srt/managers/schedule_policy.py)는
혼합 decode를 chunk 예산에서 공제하고 KV/page 경계를 검사한다.
[Sarathi-Serve](https://arxiv.org/html/2403.02310v1)는 chunked prefill과 decode 혼합의 처리량/지연
절충을 다룬다. 이 원리가 특정 P4 모델의 최적 폭이나 pipeline window를 증명하지는 않는다.

현재 P4는 upstream server의 슬롯 스케줄러를 호출하지 않는다. 기존 ordinary scheduler의
decode 예약·회전 fairness·prepare/validate/commit 경로 앞에 adapter 소유 `PipelinePolicy`를 붙였다.
phase별 참여 요청 상한을 `ceil(eligible / (window - open))`으로 유도하고, 기존 명시 한도가
더 작으면 그것을 지킨다. 16개 긴 prompt·window8·batch512에서는 fragment1을 유지하며
2요청×256행의 독립8묶음을 준비한다. 모든 요청을32행씩 한 batch에 쓰고 한 바퀴를 기다리는
이전 pure-prefill 반례를 고친 것이다. 전체 행 수와 참여 요청 수를 혼동하지 않는다.

decode 상태의 요청이 하나라도 있으면, 그 토큰이 현재 비행 중이어도 prefill 총 행을
`P4_STAGED_MIXED_PREFILL_ROWS`(실험 시작값128)로 제한한다. 실제 ready decode는 기존 scheduler가
예약한다. 이는 비선점 호출의 정적 작업량 한도이며 비용 예측/실시간 지연 보장이 아니다.
`P4_STAGED_PIPELINE_BATCHING=1`일 때만 적용하고 finite open window·positive quantum·fragment1을

### 이번 정책에 남은 비용

**행 폭, 참여 요청 수, flight 목표는 따로 선택해야 한다.** MI head native 호출은3790→28279회로 늘었다.
decode2행의 head RPC는평균26.24ms, 기준 decode16행은58.43ms다. 작은 묶음이 토큰당 싸다는 뜻이 아니다.
관측 구간의 prefix·동시 실행·요청 감소가 다르므로 이 평균을 고정비 회귀나 정밀한 matched kernel 비교로 사용하지 않는다.
파이프라인을 채울 만큼 독립 flight를 확보한 다음에는 지연 예산 안에서 decode를 더 합치는 편이 나을 수 있다.
현 정책의 `ceil(eligible/(window-open))`은 첫 안전 선택이지 비용 최적화가 아니다.

**정적128행은 지연 보장이 아니다.** Hy3 후보 mixed129행에서 head RPC2692.40ms 중 native decode가2685.29ms,
encode0.72ms, 바깥 미분류는6.16ms다. head trace19215개와 artifact span19215개의 순서·행 수를 모두 확인했다.
native decode는 CPU/GPU/내부 동기화를 포함한다. 이 관측은 다음 귀속이 native 안에서 필요함을 말하며,
1ms 재시도나 RPC wrapper를 없애면2.69초가 사라진다는 근거가 아니다. 부분 기준군의 native471/span470은
전량 대응하지 않아 `head-cost.py`가 상세 비용 대응을 거부했다.
비선점 prefill 여러 개가 decode 앞에 놓이면, 한 chunk를 제한해도 생성 대기가 누적된다.

**같은 layer 수는 같은 서비스 시간이 아니다.** Hy3 후보 pure-prefill 단계별 RPC 평균은 M42 S0/S1각5.38/5.54s,
Spark0.978s, Mac0.331s, 로컬2.910s, Ubuntu1.383s다. M42 두 단계의 전체 RPC 활성비율은92.5/95.6%다.
CPU expert offload와 host CPU/DRAM 공유가 있는 현재 컷에서 빠른 장치에 일을 더 넣으면 느린 단계 앞 queue만
늘 수 있다. CPU/GPU 각각의 병목을 확정하지는 않았으나, 서비스 시간 불균형은 관측됐다.
KV를 먼저 확보한 로컬3090은 KV14.0625GiB와 compute약3.567GiB 때문에 CPU weights약34.8GiB를 사용한다.
최대 context·resident 보장과 실제 KV pool을 구분해 계획해야 한다. 이를 몰래 줄여 GPU weight 비율을 높이지 않는다.

**ready 요청 수로 prefill의 폭을 판단하면 안 된다.** 현재 `drive.rs`의 min gate는 `ready_row_count()`의
요청 수를 사용한다. MI min4에서는 마지막2개의 긴 prompt가512행을 채울 수 있어도 다른 요청 반환을 기다린다.
pure-prefill row 충족과 decode coalescing의 최소 요청 수/대기 만료를 분리하는 반례다.
fragment1은 충분한 독립 요청이 있을 때만 파이프라인을 채운다. 한100k 요청의 선행 fragment는 아직 다루지 않았다.
입력 계정은 고쳤지만 MI agent RSS는 UNLOAD 이후에도 기준35.67GiB/후보30.88GiB 정도 남았다.
이는 heap/receipt 원인이 확정됐다는 뜻이 아니며 B2/B3/반환·broker byte 수명 게이트는 여전히 열린다.

### 산술 실패의 별도 native 대조

최신 native의 public llama API만 쓰는 단일 모델 프로그램으로 같은16개 prompt를 greedy 생성했다.
P4 stage 전달 없이 전체 모델을 같은MI250-B8장에 배치하고 각1024토큰 prefix를 받았다.
정확한 UTF-8 prompt hash와 tokenizer2885/10661을 P4 입력과 확인했다. 선두 계산은2/16통과,
14/16오류, 미파싱0으로 P4 후보와 통과 index0/5가 같다. 따라서 산술 오류는 P4 없이도 재현된다.
이 결과가 분산 수치 차이 전부를 배제하거나 전체 응답/bitwise 동일성을 증명하지는 않는다. native reference는
single sequence와 다른 logical n_batch이므로 TPS 비교가 아니다. 초기 CRLF prompt 시도는 입력 토큰 수가 달라
같은 입력 대조에서 제외하고 원자료를 남겼다. 최종16개는 `native-reference-exact/`, `native-reference-rest/`다.
P4 응답과 유효 reference 출력은 strict UTF-8이며 U+FFFD가 없다. native stderr의 GGUF vocab 표시에서 발견한
비UTF-8 byte는 출력 응답과 별개로 보존했다.

### 다음 구현의 계약과 판별 시험

현재 작업 순서는 로드맵 §0.V1.1이 소유한다. 이번 결과가 정당화하는 후속 설계는 다음과 같다.

1. **자원 수명과 대기 계측:** 실제 actor enqueue→dequeue, head monotonic issue→settle,
   미발행 이유, active/retired receipt bytes와 B2/B3 반환 예약을 결속한다. native CPU/GPU/전달을 분해한다.
   active slot 제거와 payload 최종 퇴역을 구분하고 정상/취소/replay/결과 불명에서 소비 시험·변이를 통과한다.
2. **phase별 폭·묶음·창:** prefill에는 효율적인 row 폭과 독립 요청 묶음을, decode에는 deadline 안의 coalescing을
   적용한다. hard open8은 상한이며 항상8개를 만들라는 목표가 아니다. queue가 없는 경로 지연을 가장 느린 stage의
   서비스 간격으로 나눈 값을 필요한 flight의 초기 추정으로 쓰되 byte/KV/요청 의존성으로 제한한다.
   queue를 포함한 RTT가 길어졌다는 이유로 창을 더 키우는 피드백은 금지한다. min gate도 phase별로 분리한다.
3. **누적 prefill 시간 예산:** 모델/backend/stage/phase/행 수/참여 요청/KV prefix별 비용을 예측한다.
   새 prefill을 추가했을 때 decode가 통과할 각 stage의 기존 대기·비선점 잔여 실행·추가 chunk 비용을 계산한다.
   그 예상 완료시각이 decode의 남은 지연 예산을 넘으면 prefill을 줄이거나 연기한다. P 요청에는 deficit/aging을
   적용해 기아를 막는다. 한 비선점 호출 자체가 목표를 넘으면 그 latency는 스케줄러만으로 보장하지 못한다.
4. **KV 우선의 컷/오프로딩 재계획:** weights+KV+compute+margin과 host RAM/CPU/DRAM 예산 안에서
   가장 느린 stage를 줄이는 컷을 PLAN→실제 최대 메모리→동일 부하로 검증한다. Spark/Mac 여유 활용은 별도 실험 축이다.
   100k×동시수의 수용 약속은 유지한다. 단순 layer 비례 추정은 메모리 승인으로 사용하지 않는다.
5. **실제100k와 적은 요청:** 충분한 요청에서 먼저 정책을 고정한 뒤, fragment1→2→4를 독립 비교한다.
   sequence/token-range/KV prefix 순서와 duplicate/cancel/out-of-order/RELEASE/SETTLE 안전성을 먼저 증명한다.
   node 실행1과 decode outstanding1은 유지한다. 한 긴 요청/여러 긴 요청/생성 중 긴 요청 유입/짧은 신규 요청의
   연속 도착을 분리해 TTFT·TPOT p95·정상 완료/해제·메모리 안정성을 검증한다.

## 17. 긴 prefill 다중 요청: 관측에서 도출한 배치 정책

이 절은 §12의 측정과 현재 scheduler/drive를 대조한 설계 결론이다. 새 비용 정책의 구현·실기 통과 기록이 아니다.
실행 순서는 로드맵 §0.V1.1이 소유한다. 비교 실기는 실제 최장10.6k 입력이며100k 검증으로 확대하지 않는다.

### 세 결정을 분리한다

현재 `scheduler/pipeline.rs::PipelinePolicy::select`는 eligible 요청 수를 남은 flight slot 수로 나눈다.
이는 독립 묶음을 만드는 수정이며 GPU 비용·prefix 길이·stage backlog·요청 deadline을 받지 않는다.
`drive.rs`의 phase별 발행/2ms decode coalescer도 시간 기반 prefill 정책 전체를 대신하지 않는다.

| 결정 | 목적과 변경 방향 |
| --- | --- |
| batch의 prefill 행 폭 | 한 native 호출의 효율 확보. pure-prefill은 효율 곡선이 평탄해지는 충분한 폭을 사용하고, mixed는 decode 완료시각 제약 아래 고름 |
| batch 참여 요청 수 | 한 batch가 모든 독립 요청을 outstanding으로 만들지 않도록 분리. 오래 기다린 요청의 서비스 몫을 보존 |
| pipeline의 flight 목표 | 병목 stage에 공급이 끊기지 않을 만큼 확보. 이미 바쁜 stage 앞 queue만 늘리면 추가 발행을 늦춤 |

16요청/fragment1/8flight에서 `16×32=512`는 다음 요청 묶음을 남기지 않지만 `2×256=512`는
서로 다른8개 묶음을 만든다. 행 폭을 줄이지 않고 파이프라인 깊이를 얻을 수 있다. MI의 head RPC가
193→203ms로 빨라지지 않았는데 반환 대기가1948→196ms로 줄어든 현상은 이 의존성 변화와 맞는다.
다만 전체 후보는 mixed quantum도 함께 바꿨으므로 전체 TPS70.83%를 cohort 하나의 효과로 분해하지 않는다.

충분한 independent 요청이 있으면 우선 fragment1을 유지한다. 1–2개 긴 요청만 남으면 최대 독립
flight도 작아진다. 그 경우에만 같은 요청의 다음 prefill fragment를 검토한다. 토큰은 알려져 있어도
각 stage의 이전 prefix KV 완료·token-range 순서가 필요하다. decode는 이전 sampled token이 필요하므로
요청당 outstanding1을 유지한다. 현재 pipeline policy는 multi-fragment를 명시적으로 거부한다.

### 행 제한을 누적 서비스 시간 제한으로 발전시킨다

prefill만 있는 구간은 큰 chunk로 native 호출 횟수를 줄인다. decode와 공존하는 구간에서는 다음
decode가 지날 경로에 이미 들어간 prefill까지 계산해야 한다. ready decode가 잠시0이어도 이전 decode가
비행 중이면 다시 도착할 decode를 고려한다. 한 번 실행한 native 호출은 이 정책에서 선점할 수 없다.

adapter 내부의 비용 입력은 stage/backend/weight 배치/host CPU 예산, prefill·decode 행 수, 참여 요청 수,
요청별 KV prefix, 실제 attention n_kv/QK shape와 kernel이다. 같은128행이라도10k와100k prefix의 비용은
같다고 볼 수 없다. dense causal attention의 유효 query-key 쌍은 대략 `q*L + q*(q+1)/2`지만,
이는 유효 attention 작업의 구조 설명이며 masked block·padding·unified pool·MoE·CPU offload를 포함한
실제 kernel 시간 식이 아니다. 새로운 길이/backend 비용은 직접 측정하고 예측 오차를 남긴다.

동일 크기 batch를 독립 stage가 하나씩 처리하고 비용이 일정하다는 단순 모델에서는
`최대 batch/s ≈ 1/max(stage service time)`이다. queue를 제외한 경로 지연을 이 발행 간격으로 나눈
값은 필요한 flight 수의 초기 추정으로만 쓴다. 실제로는 공유 GPU/CPU/DRAM 및 edge 자원도 제약한다.
queue 때문에 RTT가 늘었다고 flight를 늘리면 혼잡을 더 키우므로 이 방식으로 창을 적응시키지 않는다.

후보 batch b가 stage s에서 끝날 예상시각은 다음 순서 제약을 적용한다.

```text
finish[b,s] = max(arrival[b,s], finish[앞서 예약된 작업,s]) + predicted_service[b,s]
arrival[b,s+1] = finish[b,s] + predicted_transfer[b,s]
```

실행 중 작업의 남은 시간과 이미 발행된 batch를 먼저 반영하고, 후보 prefill을 넣었을 때 각 decode의
예상 완료시각이 지연 목표를 넘는지 검사한다. 넘으면 chunk를 줄이거나 이번 prefill을 연기한다.
이는 head에서 순서를 예측하는 정책이며 노드 간 wall clock을 직접 빼는 계측이 아니다. 입력·KV 순서나
이미 발행한 membership을 뒤집지 않는다. 예측 오차와 최소 native 호출 지연 때문에 hard real-time 보장은 아니다.

동작은 다음과 같이 구성한다.

1. 자원 예약·KV prefix·의존성이 허용하는 요청만 후보로 삼는다.
2. 만료가 가까운 decode 묶음을 고르되 모든 독립 decode를 한 묶음에 모아 직렬화하지 않는다.
3. prefill의 누적 미서비스량과 대기시간으로 요청을 고른다. 공정성은 행 수뿐 아니라 예상 병목 서비스 시간을
   단위로 부과하고 실제 비용으로 보정한다. 거부된 계획은 몫을 소비하지 않는다.
4. discrete chunk 후보를 각 stage의 기존 작업 뒤에 가상 배치해 decode 완료시각과 prefill 처리율을 비교한다.
   native 호출 효율이 좋아지는 충분한 폭 중 지연·메모리 예산을 만족하는 후보를 선택한다.
5. flight·edge/receiver bytes·KV·필수 반환 예약을 함께 확보한 뒤 원장과 membership을 확정한다.
   완료 때 실제 비용·예측 오차를 반영하고 다음 선택을 갱신한다.

decode를 영구 우선하면 prefill이 굶고, prefill의 최소 서비스 몫만 강제하면 과부하에서 decode 목표를
넘을 수 있다. 따라서 bounded aging/서비스 몫과 admission을 함께 사용한다. 지속 도착량이 병목의 처리
용량을 넘는 경우 유한 메모리와 모든 요청의 유한 대기시간을 동시에 보장할 수 없으므로 수용 대기/거부를
명시한다. 긴 입력을 짧게 바꾸거나 resident 약속을 몰래 낮춰 이를 숨기지 않는다.

이 방향은 [Sarathi-Serve](https://arxiv.org/abs/2403.02310)의 chunked prefill·지연을 제한한 혼합 배치와
[vLLM의 chunked prefill](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill)의
decode 우선/잔여 token budget 원리를 사용한다. 단일 실행기의 모든 decode 선택을 P4에 그대로 옮기지 않고,
독립 요청 묶음·stage 누적 서비스·finite flight를 추가하는 것은 이번 코드/실측에 근거한 설계 판단이다.

### 실행 상태에 따른 선택 명세 (2026-09-12 분석, 미구현)

효율적인 행 폭은 최대 UBATCH와 같다고 가정하지 않는다. 같은 backend/배치 배정과 prefix 구간에서
행당 native 비용 및 병목 처리율이 좋아지는 폭을 구하고, 지연 제약 안에서 그 폭을 유지한다.
다음 표는 §20의 대조에서 도출한 의사결정 명세이며 새 알고리즘의 성능 승인이나 완료 기록이 아니다.

| 현재 상태 | 선택할 행동 | 피해야 할 결과 |
| --- | --- | --- |
| 긴 prefill 다수, decode 없음 | 큰 행 폭을 유지하며 active/ready/inflight를 나눠 독립 요청 묶음을 순환 발행 | 모든 요청을 한 배치의 outstanding으로 묶음 |
| decode와 긴 prefill 공존 | 기발행 작업 뒤의 decode 완료시각을 예측하고 prefill chunk를 축소/선택 | 큰 chunk 전체를 거부하여 작은 decode만 반복하거나 prefill 기아 발생 |
| 병목 stage가 공급 부족으로 유휴 | 기존 안전 창 안에서 독립 묶음 공급을 늘림 | head 배치 채움률만 높여 downstream을 비움 |
| 병목 stage는 연속 실행, 앞 queue만 증가 | 추가 발행을 억제하고 cut/offload/공유 CPU·DRAM 병목을 개선 | 관측 RTT 증가를 근거로 flight 목표를 계속 키움 |
| 긴 요청1–2개, fragment1 의존성으로 유휴 | stage별 prefix KV 완료와 순서를 증명한 뒤 bounded prefill fragment 중첩 | 입력 토큰이 알려졌다는 이유만으로 KV 순서/취소 검사를 제거 |
| KV/반환 예약 부족 | 외부 대기량을 제한하고 수용 대기/거부를 명시 | 선언 resident를 실제 동시 수용으로 보고하거나 지속 swap/recompute를 포화로 승인 |

단순한 균일 배치/독립 장치 모델에서 필요한 flight 수의 시작점은
`ceil(큐 대기를 제외한 한 바퀴 지연 / 병목 자원의 batch 처리 간격)`이다.
이 값은 측정으로 보정할 추정이며 기존 resource credit 상한을 늘리는 권한이 아니다.
한 장치에 여러 stage가 있거나 CPU·전송 자원을 공유하면 그 자원의 합산 작업도 병목 계산에 넣는다.
선택 목표는 병목 공급 공백 감소와 정상 응답 처리율이다. batch 행 채움률·open 창 채움률·빠른 GPU의
사용률 각각을 최대화하는 것은 지연/메모리 예산과 충돌할 수 있다.

### Hy3는 느린 단계의 작업 배치도 함께 바꿔야 한다

Hy3 pure-prefill RPC는 M42 두 stage가5.38/5.54s, Spark0.978s, Mac0.331s다. 느린 stage가 계속 일하는
상태에서 빠른 stage에 같은 작업을 더 공급할 수는 없다. 같은 비용이 반복된다는 단순 모델에서 Mac의
RPC duty는0.331/5.54≈6%여도 전체 pipeline은 병목 용량에 도달할 수 있다. 이는 GPU 사용률 예측이나
이번 전체 실기의 duty 계산이 아니라 불균형의 의미를 설명하는 예시다. 모든 장치100%를 목표로 queue를
늘리면 처리량은 그대로인 채 TTFT·ITL·보관 메모리만 늘 수 있다.

따라서 M42의 CPU 연산/DRAM·GPU/동기화 비용을 나눈 뒤 가장 느린 stage의 비용을 낮추는 합법적 cut과
weight 배치를 비교한다. GPU에100k×보장 동시수의 실제 KV·compute·margin을 먼저 확보하고, 남은 용량에
weights를 배치한다. host RAM에 놓인 experts의 실행 비용과 두 stage의 CPU 자원 경합도 계산한다.
Spark/Mac으로의 이전은 실제 메모리·지원 kernel·네트워크 경계를 통과한 후보만 허용한다. 모든 stage를
동일 layer 수로 만드는 것이 목표가 아니며 offload 허용 자체가 속도 개선을 보장하지 않는다.

## 18. 제품 root·제어·TCP의 실제 반환 소유권

기준 `3efd668c12964bcaef4f6a99501840bbfc9ad759`의 main/GitHub 일치와 clean을 재확인했다.
코드 반례는 control reply의 broker Full 후 폐기, TCP write 실패의 현재/대기 Event 폐기,
snapshot만 보고 node task를 abort하는 DELETE다. 이 단위는 `target/v11-owned-runtime-20260911/`에 기록한다.

### 구현과 계약

product event root가 owned broker/node/llama adapter를 선택한다. per-store Event bytes 기본256MiB와
retained count65536은 producer→queue→소비 중 원본을 함께 계산한다. CREATE의 입력/완료 저장소도
별도 같은 기본값을 가지며 양의 환경설정/명령 필드로 구성한다. 물리 queue 기본65536·wire ceiling2GiB는
그대로다. 개별 Event가 bytes 한도를 넘으면 원본과 거부를 보존한다. 전체 RSS/미래 출력의 보장은 아니다.

control Full에서 input과 reply를 유지하며 성공 뒤에만 다음 command를 읽는다. 영구 실패 후 node owner·
미처리 receiver와 원본은 root가 보관한다. socket queue/현재 write에서도 같은 claim을 이동한다.
실패한 writer는 현재 원본(전송 결과 불명)과 미시작 receiver를 보존한다. 자동 reconnect/replay로 뒤 이벤트를
앞서 보내지 않는다. healthy input half-close는 출력 route를 닫지 않는다. DELETE는 ingress pause 후
semantic state·task 상태·원본 count를 함께 확인한다. 중립 core는 pause만 제공하며 payload를 읽지 않는다.

### 실제 소비 검증 묶음

- 제품 root/TCP/실제 llama Worker: CREATE→opaque command의 실제 Worker 오류→OUTER write 및 별도 idle DELETE.
- 두 실제 TCP agent: opaque command와 원본 causation/source를8회 왕복, backend 해석은 control/adapter에만 존재.
- TCP ingress queue1/retained1: Full 중 원본 유지, dequeue 뒤에도 소비 claim을 놓기 전 다음 수용0,
  퇴역 후 두 원문을 순서대로 전달. 입력 half-close 뒤에도 같은 연결로 응답 수신.

decode보다 앞선 비선점 prefill이 쌓인다. 이번 첫 단위는 실제 downstream Frame 호출의 단조시계
시간을 head로 돌려보내, 각 stage의 미완료 open-prefill 예상 비용+후보 비용을 계산한다.
모든 비용이 알려져 있고 어느 stage가 soft 예산을 넘으면 prefill을 제외한 ready decode를 다시 계획한다.
거부된 후보는 fairness·flight·요청을 commit하지 않는다. 비용 표본은 KV/flight/edge 반환 권한이 아니다.

계산만 feedback Event를 보낸다. decode-only마다 불필요한 event를 추가하거나 비용 profile을 밀어내지 않는다.
출처·load/session·정확한 execution 목록/행 membership·중복/충돌을 검사한다. history128/profile256,
동일 phase별 행 수/요청 수/최대 position의2진 구간별 최근8비용의 최댓값으로 제한한다.
표본이나 open membership을 모르면 `cold`로 표시하고 기존 bounded 정책을 쓴다. 이전 prefill이 모두

   인코딩해 반환한다. 행 배열의 앞에 decode가 있어도 그 결과를 prefill 계산 중 먼저 전달하는 구조가 아니다.
   앞으로 넣을 생성의 우선순위로 이미 native가 실행 중인 큰 prefill을 중단할 수도 없다.
3. `mixed_prefill_rows`는 문맥 위치를 보지 않는 고정 행 수다. full causal attention에서 길이 L의
   기존 KV 뒤에 c개를 추가하면 attention의 유효 query/key 쌍은 대략 `c*L+c*(c+1)/2`이다.
   따라서 1k 위치의128행과96k 위치의128행은 같은 일이 아니다. SWA/MLA/recurrent는 모델별 비용을 사용해야 한다.
4. `service.rs`는 이미 열린 prefill의 stage별 예상 비용을 합산하지만 decode-only 비용은 학습하지 않는다.
   실행 중 작업의 잔여·단계 간 도착·새 decode의 tail 완료시각을 계산하지 않으며, 큰 후보를 거부해도
   더 작은 chunk를 찾아 다시 넣지 않는다. 기존250ms arm 악화는 이 구체적 정책의 반례다.
5. 일반 attention과 equal-width recurrent/hybrid는 합법적인 물리 배치가 다르다. 후자는 decode1행과
   prompt를 같은 equal-width 호출에 넣으면 prompt도1행으로 잘릴 수 있어 현재 phase를 분리한다.
   동일한 서비스 목표를 적용하되, 모든 backend에 동일한 혼합 모양을 강제하지 않는다.

### 수정할 정책

**생성에 남는 행을 주는 것이 아니라 생성의 다음 완료시각을 먼저 보호한다.** 다음 발행의 생성 참여자는
준비됨·의존성 해소·KV/반환 예약 가능 조건을 만족해야 한다. 오래 기다린 생성부터 선택하고,
추가 생성이 시간/물리 예산에 들어가는데도 순간 free 수만으로 제외하는 경우를 없애는 방향으로 대조한다.
마감이 다른 생성 집단을 나눌 필요가 있으면 여러 bounded 배치로 즉시 흘린다. 모든 생성을 하나로 합쳐
그 반환을 기다리는 전역 장벽을 새로 만들지 않는다.

그 뒤 prefill의 후보 chunk를 선택한다. 후보의 조건은 행 상한뿐 아니라 **같은 배치와 이미 발행된 배치에
영향받는 생성 요청의 예상 완료시각**이다. stage s의 배치 j 완료 예측은 실제 큐 순서에 대해
`F[j,s] = max(arrival[j,s], F[j-1,s]) + estimated_service[j,s]`로 갱신하고, 다음 stage 도착에는
전송을 더한다. 마지막 stage 뒤 sampler/반환 지연도 포함한다. 각 장치의 duration과 정렬된 이벤트를
사용하고 다른 호스트의 동기화되지 않은 wall clock을 그대로 빼지 않는다. 이미 commit된 순서를 뒤집지 않는다.

후보 탐색은 현재 안전 상한 안에서 시행한다. 문맥 길이·P/D 행 수·요청 수·backend·stage·오프로딩 상태를
반영한 예측의 오차 여유까지 만족하는 범위에서 처리량이 높은 chunk를 선택한다. 비용의 단조성이
확인되면 이진 탐색을, kernel 전환 등으로 비단조이면 검증된 후보 집합을 사용한다. 데이터가 부족할 때는
기존의 보수적 상한을 사용하고 “deadline 보장”이라고 표시하지 않는다. 필요한 경우 prefill0도 허용하지만
decode-only 자체가 목표를 넘는 상태는 과부하/배정 병목으로 명시한다.

구현 시 `OrdinaryLimits`의0은 현재 “무제한/별도 제한 없음”이므로, prefill0 허용을 기존 필드에0을
대입해 표현하면 반대 동작이 된다. 명시적인 금지/유한 예산 표현이나 prefill 수요 제외를 사용해야 한다.
또한 마지막 prompt가 이미 flight에 있어 곧 첫 생성이 준비될 경우도 예측 지평에 넣는다.
현재 ready decode0이라는 이유만으로 긴 prefill을 미리 창 가득 쌓지 않는다.

긴 prompt가 여러 개이면 한 배치에 전부 조금씩 넣어 다음 발행까지 전부 잠그지 않는다. §22처럼 독립
집단을 유지하고, 각 집단 안의 행 폭은 계산 효율이 충분한 크기로 만든다. 동시에 prompt별 누적 서비스
부족분과 대기시간으로 다음 집단을 선택한다. 단순 token 공정성이 아니라 예측/실측 비용 단위를 사용한다.
새 요청 수용량이 지속적으로 처리량을 넘으면 decode 지연과 prefill 무기아를 함께 보장할 수 없으므로
수용 대기·메모리/반환 예약·과부하 판정을 결속한다.

**“포화”의 대상은 한 배치의 행 상한이 아니라 병목 장치의 유효 처리능력이다.** 같은 크기 배치의
무대기 왕복시간이 R, 병목 stage 서비스가 S라면 `ceil(R/S)`는 필요한 독립 flight 수를 가늠할 출발점이다.
이는 균일 정상상태의 근사이며 관측 queue 대기를 포함한 R로 상한을 무한히 늘리는 제어식이 아니다.
요청·KV·byte가 허용하는 기존 창 안에서 검증하고, 병목이 이미 바쁘면 추가 flight 대신 큐 지연을 줄인다.

Hy3의 느린 CPU 전문가 stage가 계속 일하고 다른 GPU가 기다리는 경우에는 배처만으로 모든 장치를
최대 사용률로 만들 수 없다. KV를 GPU 메모리에 우선 예약하고 compute/flight 여유를 뺀 뒤 weight를
배치하되 stage의 실제 시간을 기준으로 컷과 CPU/장치 배정을 조정한다. Mac unified memory는 RAM과
VRAM을 별도 물리 용량처럼 더하지 않는다. 한두 개100k prompt의 fragment1 의존성은 별도 상한이며,
동일 요청의 다중 fragment는 prefix-KV 순서·취소·반환을 증명한 뒤 허용한다.

### 생성 지연의 경로별 귀속

동일 physical execution에 연결된8개 stage span을 모두 결속했다. 한 호스트의 시계에서 head RPC

execution ID 중복 없음, 단계 사이 음수 간격 없음을 검사했다. RPC 내부는 native/backend 서비스이며

### 인과 해석: 생성 우선과 전량 합류는 다른 결정이다

### 다음 수정의 계약과 판별 순서

현재 실행 순서는 로드맵 §0.V1.1이 소유한다. 이 절은 다음 구현의 근거와 실패 조건을 정한다.

1. **생성 묶음 유지:** 선택한 독립 묶음 안에서는 D를 먼저 배정하되 전체 ready D를 반드시 한 Frame에
   넣는 조건은 철회한다. 순간 vacancy만으로 묶음을 병합하지 않고 admitted ready/inflight 인구를 사용한다.
   P가 없어도16개 D·기존 창8에서 첫 tail 전 여러 flight를 발행하고 반복 반환 후에도 합쳐지지 않는
   실제 소비 반례를 만든다. 여러 D를 함께 계산하는 효율과 독립 flight를 유지하는 효율을 함께 비교한다.
2. **폭·깊이·청크 공동 선택:** 측정한 stage별 서비스 `t_s(b)`에 대해 `L=sum(t_s)`, `S=max(t_s)`를
   계산하면 동일한 독립 배치의 공급 깊이 `ceil(L/S)`는 초기 참고값이다. 유한 창/실제 수요/자원 상한으로
   자르고 실제 통신·dispatch·공유 장치 비용을 넣어 재평가한다. 이상적인 처리량 식은
   `b * min(M/L, 1/S)`이며 성능 약속이 아니다. 생성 요청 수 N에서는 독립 묶음 M도 대략N/b에 제한된다.
   이 때문에 큰 b를 고르면 kernel 효율이 올라도 M이 줄어 전체 파이프라인이 빌 수 있다.
3. **남는 공간을 시간 여유로 정의:** D의 ready 시각부터 요청별 목표까지 남은 시간에서 기존 stage 작업의
   실행 잔여·전송/dispatch·반환을 뺀다. 허용되는 후보 중 처리할 P 토큰이 큰 청크를 고르되, 최소 행 채움을
   강제하지 않는다. 초기 예측에는 별도 calibration 예산을 두고 첫 짧은 요청들이10초 이상 밀린 반례를 닫는다.
   실제100k에서는 같은1개 D도 KV 읽기 비용이 커지므로 행 수만으로 값싼 작업이라고 가정하지 않는다.
4. **프리필 기아·메모리:** P 공정성은 요청 수/행 수뿐 아니라 사용한 stage 시간과 대기 나이로 계산한다.
   짧은 prompt 완료 기회와 긴 prompt의 최소 진행을 함께 보장한다. 전체 KV·pending prompt·반환 byte
   예약 안에서만 admission/flight를 허용한다. RAM offload는 느린 stage 비용에 포함하며 큐만 늘려 숨기지 않는다.
5. **회귀 검증:** 같은 입력/출력 토큰 수의 성능 진단과 자연 EOS/내용 검증을 별도 arm으로 수행한다.
   pure-decode 무회귀, mixed ITL 개선, prefill 처리량/TTFT 손실, 초기8건의 first-output을 함께 판정한다.
   GPU 사용률이나 mixed 수 하나로 승인하지 않는다. 효과가 있더라도 latency와 goodput의 손익으로 보고한다.

### 무엇이 달라졌는가

활성 생성16·prefill 없음인 실제 관측 구간에서 기존1684회는 폭1/2/3이231/1221/232회였다.
