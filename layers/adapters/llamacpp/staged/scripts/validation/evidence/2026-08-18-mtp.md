## Why this is not real MTP

The prepared compatibility source contains the MTP API enum and the
speculative implementation:

```text
.cache/llama-pipeline-upstream/3e3a7a416d-282f5e1fbdd7/include/llama.h
  LLAMA_CONTEXT_TYPE_MTP = 1
.cache/llama-pipeline-upstream/3e3a7a416d-282f5e1fbdd7/common/speculative.cpp
  cparams.ctx_type = LLAMA_CONTEXT_TYPE_MTP
```

The staged runtime does not use that path. In
`staged/server/src/runtime/llama_stage_runtime.cpp`, `load()` directly calls
`llama_model_load_from_file()` and `llama_init_from_model()`. Its context
parameters come from `common_context_params_to_llama()`, whose implementation
does not set `ctx_type`; the MTP assignment occurs only in the separate
`common_speculative_init_result` path.

The staged server has no draft-model ownership, speculative driver,
proposal/verification loop, acceptance telemetry, or MTP execution path.
`--spec-type draft-mtp` is accepted by the shared common argument parser, but
the staged server now exposes that distinction explicitly. Its report is:

```text
mtp_parser=1;mtp_execution=0;speculative_parser=1;speculative_execution=0;
normal_decode_execution=1;mtp_requested=1;speculative_requested=1
```

When MTP/speculative options are requested for a normal startup, the server
prints the report and exits with code `6` and
`CAPABILITY_UNAVAILABLE`; it does not silently run ordinary decode while
ignoring the requested mode. `--validate-plan` exits successfully after
printing the same report and does not load a model. The report is also included
in `HELLO` for an ordinary loaded stage.

The implementation and tests are in:

```text
staged/server/src/server/plan.cpp
staged/server/src/server/capability_test.cpp
staged/scripts/validation/validate-mtp-speculative-capability.mjs
```

The C++ regression matrix now covers all parser spellings, not only
`draft-mtp`: `draft-simple`, `draft-eagle3`, `draft-mtp`, `draft-dflash`,
`draft-dspark`, `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`, `ngram-mod`,
and `ngram-cache`. Every spelling remains `speculative_parser=1` and
`speculative_execution=0`; `draft-mtp` additionally remains
`mtp_parser=1;mtp_execution=0`.

## Blockers and safe scope

Real MTP/speculative execution remains unavailable by the staged runtime
boundary, not by model availability. A targeted source audit on 2026-08-18
confirmed that enabling the parser flag would not make the feature execute:

1. MTP tensors are built by the upstream architectures with `il =
   hparams.n_layer()` (and, for multi-head variants, `n_layer() +
   nextn_layer_offset`). The staged loader patch classifies `NEXTN_*` tensors
   as `LLM_TENSOR_LAYER_REPEATING`, then owns them only when
   `layer_begin <= tn.bid < layer_end`. The same patch validates
   `layer_end <= hparams.n_layer()`. Consequently a tail window ending at
   `n_layer()` still does not own the MTP-head tensors whose block id starts at
   `n_layer()`. This cannot be repaired in the staged server after
   `llama_model_load_from_file()`; it requires a compatibility-layer ownership
   change or a separate auxiliary-head load contract.
2. The upstream `common_speculative` API is available to the server link, but
   its real initialization creates a second context (`ctx_dft`) and its loop
   calls `common_speculative_draft()`, target verification, acceptance, and
   sequence rollback. The staged runtime owns only one partial `llama_context`
   and has no draft-context owner.
3. The staged HOP carries one sequence's cut-set descriptors and returns one
   sequence result. It has no proposal list, accepted-token count, target/draft
   phase, or rollback checkpoint identifier. Returning only the last accepted
   token would silently drop accepted draft tokens, so it is not a valid
   implementation.
4. Current KV persistence serializes ordinary sequence state. It does not
   define atomic fork/rollback of both target and draft contexts, which the
   upstream speculative loop requires after partial acceptance.

This audit intentionally does not turn the capability bit on. The safe
increment already implemented is the explicit parser-only admission gate:
every supported parser spelling is covered by the C++ capability matrix test,
and a requested execution exits before model loading with
`CAPABILITY_UNAVAILABLE`. The current capability result is therefore
**parser-only**, not “execution passed”.

### Smallest viable implementation order

The following is the minimum sequence for a real implementation, without
modifying the upstream checkout:

1. Extend the versioned compatibility layer (outside upstream) with an
   auxiliary MTP ownership/load mode and expose the resulting head tensors as
   staged inputs/terminals.
2. Add a staged speculative session that owns target and draft contexts and
   exposes begin/draft/verify/accept/rollback operations.
3. Extend the staged wire and its adapter together for multi-token proposals,
   accepted-token lists, and checkpoint identity. A server-only change cannot
   be end-to-end usable because the current adapter cannot send or consume
   those operations.
4. Only then advertise execution capability, gated by a HELLO matrix and an
   actual model test covering acceptance, rejection, rollback, and unload.
