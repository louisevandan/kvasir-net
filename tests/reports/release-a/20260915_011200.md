## Mac 실행 환경과 반환 경로

처음 분리 실행한 Mac agent는 실제 P4 peer 송신에 `No route to host (os error 65)`를 남겼다.
같은 Mac의 Python, 새 Rust 표준 TCP 및 같은 Tokio library의 TCP 검사는 성공했다.
기존 Rust agent의 재조회와 GUI LaunchAgent 실행도 같은 P4 반환 검사를 통과하지 못했다.
특정 개인정보/방화벽 설정을 원인으로 단정하거나 변경하지 않았다.

**같은 바이너리를 SSH 세션에 연결한 foreground process로 실행한 뒤 두 Mac의 P4 왕복이 성공했다.**
데이터 경로는 TCP LAN이며 SSH 터널·proxy가 아니다. SSH는 프로세스의 실행 세션만 유지한다.
Mac20/21은41993, 나머지 다섯 호스트는41991에서 전체7개 분할 edge와 반환을 실제 INSPECT로 검증했다.
실패한 분리 agent와 시험 GUI LaunchAgent/plist는 제거했다. 기존 설치 앱과 NAS 설정은 유지했다.

## 최종 회수와 기존 제어 경로

두 arm 모두 UNLOAD/DELETE 후 후보7/7 INSPECT nodes=[]와 native child0개를 확인했다.
시험 agent7개와 소유 GPU sampler를 종료했고 Windows 임시 task·방화벽 rule을 제거했다.
로컬 `target/debug/p4-agent.exe`를 원본 SHA256
`d84f9390ed7bd1717ae2e5eb6478c6caff03ec21fe0c0d8817f39fe9e976757d`로 복원·대조했다.
최초 복원은 종료 직후 파일 잠금으로 실패했고, 잠금 해제 뒤 재복원 성공을 별도 보존했다.
원격 Windows의 최초 자식0 guard는 시스템 conhost만 남아 거부했다. 해당 PID·경로·부모를
확인한 뒤 후보 agent를 종료했고 conhost도 사라졌다. 모델 자식을 무시한 강제 종료가 아니다.

물리9대의 P4 native는0개였다. 기존 등록 agent 중5개는 즉시 INSPECT nodes=[]였지만
Spark/Ubuntu의 구형 agent는 다시 timeout이 발생했다. 두 TCP listener는 Recv-Q129/Send-Q128과
다수 CLOSE_WAIT를 보였다. 요청 발생 주체와 영구 해결은 미판정이다.
모델 자식0을 확인하고 동일 원본 바이너리·argv·cwd·환경을 보존해 두 agent만 재시작했다.
Spark PID1103448→1287453, Ubuntu PID3787675→307384다. 이후 실제 등록7/7 INSPECT nodes=[]와
재시작 호스트의 native0을 재확인했다. 기존 설치 앱과 NAS 설정은 유지했다.

이는 제어 응답의 cold recovery이며 영구 transport 수정이나 과거 요청·KV 정산 수용이 아니다.
TCP half-close는 정상 지연 출력에도 사용되므로 EOF 즉시 route를 버리는 수정은 적용하지 않았다.
