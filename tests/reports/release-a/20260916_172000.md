## 관측: 원본과 분리 진단

기존 case-04/06의 정확 프롬프트·원본 응답 해시를 재사용했다. 원본 medium/long의 전력값은
총 **6행 전부** 오라클과 달랐다. 원본 에너지는 6행 전부 `모델이 낸 잘못된 전력 × 원자료
시간`과 일치했다. 따라서 에너지 배수 계산보다 앞선 전력값 결정이 실패 지점이다.

## 원인 범위와 다음 조치

확정된 **관측 가능한 원인**은 모델 생성 결과의 정수 계산 오류다. P4의 transport·정산은
그 출력이 의미상 정답인지 계산하지 않으며, EOS를 정상 terminal로 전달했다. 이 경계가
오답을 정상 서비스 응답으로 노출했다. 신경망 내부에서 특정 숫자를 선택한 미시적 이유,
예를 들어 양자화의 어느 tensor나 어떤 attention 경로 때문인지는 이번 시험으로 판별할 수
없다. 그런 추측을 코드 원인으로 보고하지 않는다.

수정 방향은 두 책임을 분리해 설계해야 한다. 정확한 산술이 제품 계약인 작업에서는
원자료 추출의 신원을 검증하고 곱셈·단위·경보 판정을 **결정론적 계산 주체**가 수행하거나,
최소한 생성값을 독립 계산해 불일치를 정상 완료로 반환하지 않도록 해야 한다. 이 계약을
generic P4 원장/transport 안에 임의로 넣지 않는다. 출력 계약·오류 terminal·호출자 경계를
설계하고 제거 변이로 검증한 뒤, 같은 엄격한 오라클을 유지한 단일 호스트 3/3과 새 H0
봉인, 분산 I0 재수용 순서로 진행한다. 모델 계산값에 맞춰 오라클을 수정하거나 요청을
줄이지 않는다.

이번 진단은 원본 프롬프트의 숨겨진 중간 추론을 직접 관찰하지 못한다. E/C/T는 사전 봉인된
서로 다른 **진단 입력**이며, 원본의 모든 내부 연산을 재구성했다고 주장하지 않는다.
그러나 C와 T의 독립 반례는 정확 산술 실패를 원본 길이·분산 경로와 분리해 재현한다.

## 재현성

`diagnose-i0-answer.py prepare`로 기존 corpus-v2와 원본 응답에서 입력 6개를 만들고,
같은 스크립트의 `tokenize`를 위 SHA의 원격 tokenizer에 실행했다. `run-i0-answer-probes.py`는
manifest/토큰 ID·서버 해시·port·단일 load·고정 순서를 사전 검사하고 응답을 하나씩
보존했다. 같은 `diagnose-i0-answer.py judge`를 원자료에 실행한 판정은 위와 같다.
재실행은 새 실기 횟수로 기록해야 하며 결과를 보고 probe 문장을 바꾸지 않는다.
