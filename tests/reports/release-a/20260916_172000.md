## Observation: original versus separated diagnosis

The exact prompts and original response hashes of the existing case-04/06 were reused. In the original medium/long, the power values
differed from the oracle in **all 6 rows**. The original energy matched `the wrong power the model produced × the raw-data
time` in all 6 rows. The failure point is therefore the power value decision, which comes before the energy multiplication.
The original long also wrongly reported `pressure_alarm` as false at 134 kPa and wrapped the JSON in a code fence.

Representative counterexamples: medium T recorded the fact `R00196: 58 A, 52 milliohms` exactly but

**It is wrong even in the short C, and it is also wrong in T, where the same response states the facts correctly.**
Long-context retrieval failure or distributed transport alone cannot explain these counterexamples.

## Scope of the cause and next steps

The confirmed **observable cause** is an integer arithmetic error in the model's generated output. P4's transport and settlement
do not check whether that output is semantically correct, and they passed EOS on as a normal terminal. This boundary
exposed a wrong answer as a normal service response. The microscopic reason the neural network picked a particular number inside,
for example which quantized tensor or which attention path is responsible, cannot be determined by this test.
Such speculation is not reported as a code cause.

The fix must be designed with two responsibilities kept apart. For work where exact arithmetic is the product contract,
the identity of the raw-data extraction must be verified and the multiplication, units and alarm decisions must be performed by a **deterministic compute owner**,
or at minimum the generated values must be computed independently so that a mismatch is never returned as a normal completion. This contract
is not dropped ad hoc into the generic P4 ledger/transport. After designing the output contract, the error terminal and the caller boundary
and verifying them with removal mutations, proceed in order: single-host 3/3 with the same strict oracle, a new H0
seal, then distributed I0 re-acceptance. Do not adjust the oracle to the model's computed values or shrink the
requests.

This diagnosis cannot directly observe the hidden intermediate reasoning of the original prompt. E/C/T are separate pre-sealed
**diagnostic inputs**, and there is no claim that every internal operation of the original was reconstructed.
However, the independent counterexamples in C and T reproduce the exact-arithmetic failure separately from the original length and the distributed path.

## Reproducibility

the same script's `tokenize` was run on the remote tokenizer with the SHA above. `run-i0-answer-probes.py`
prechecked the manifest/token IDs, server hash, port, single load and fixed order, and preserved the responses
one at a time. The judgement from running the same `diagnose-i0-answer.py judge` on the raw data is as above.
A rerun must be recorded as a new real-hardware attempt, and the probe wording must not be changed after seeing the results.
