## Separating causes and refutation

An independent llama-server with the same GGUF was run on Spark. It is a build that binds the working tree
changes to upstream pin `451b89b`, and nothing was compiled or inferred on this PC. Sending the previous input unchanged,
medium produced the same wrong JSON, and long was also wrong. For these two wrong answers, the hypothesis
that distributed transport alone is the cause is therefore refuted. The no-thinking
assistant suffix of the model's GGUF chat template is `<think>\n\n</think>\n\n`, but the corpus generator appended
`<think></think>`. This was fixed to the exact suffix and a static counterexample was added. However, it was **not confirmed as
a sufficient cause.**

The corrected corpus v2 was re-tokenized in full, all 64 requests, with the remote original tokenizer. Compared with before, the 64 requests'
oracles, raw data, arrival and class are identical; only the prompt hashes all changed. The medium raw data is
`target/release-a-i0-v5-20260916/corpus-v2/`, `corpus.json` SHA-256
`e9760a98ec190e537ff3203f01ea45e7d73033ced14be52d09a768a7451f815f`, tokenizer
SHA-256 `fba7e68f6442312155c355e015de2227e9d30c725e1f310bbca6e76cd24a6311`.
This v2 has not been sealed in a new H0, so it was not used in a distributed run.

The exact corrected prompts for case-00/04/06 were submitted sequentially to the same standalone model, at 2,782/32,000/100,038
tokens respectively. For all three responses, the sent prompt and the received prompt matched byte for byte, and each ended in EOS.
The actual result of the automatic capability gate is `case-00 PASS`, `case-04 oracle_mismatch`,
`case-06 invalid_json`, i.e. **1/3**. medium returned 78,400 mW for the first row; the correct answer is
40,768 mW. long returned a JSON code fence and wrong arithmetic and alarms. The response JSON SHA-256 values are
case-00 `d20f706887646cc151eb91bac0467d73b9d1930a83eb2adcad972afe5c359e01`,
case-04 `2f8785419b0268ba77ae6e52eaa8bfb455d461949de5dc139290414711570838`,
case-06 `2841abd701049bae3cba5655f4e5c92ff32c6a9de89e80af0adfa6cd842a1a8a`.
The original responses are preserved in `target/release-a-i0-v5-20260916/reference-v2/`.

The single-host model/input contract itself does not meet this correct-answer requirement. `judge-reference-capability.py`
checks prompt, original token count, EOS, JSON and oracle together and rejects 7 independent weakenings.
Until this gate is GREEN, distributed I0 is not repeated with the new corpus. Changing the prompt wording
to fit the results or loosening the oracle is not accepted. If exact arithmetic is required as a product contract,
the authority to deterministically compute and verify checkable values from the input, and the responsibility of the model output, must be
designed and then proven in a model-independent test. Model guesses are not treated as an algorithm.

## Reclaim, verification and first next action

The standalone server was stopped with TERM after checking the run-owned PID 2995099, the exact executable and port 62005, and
the port and 0 GPU compute processes were confirmed. The Spark protected agent PID 1287453 and :52005 are alive.
The task agents, natives, listeners and tunnels of the first distributed run on Spark/Mac20/Mac21 are at 0 per the separate normal reclaim
evidence. No other session's processes were stopped.

Local static tests passed: corpus 4/4, I0 judge self-test 12/12 and capability gate weakenings 7/7.
The actual capability gate, as intended, returned exit code 1 and per-case RED. While preparing the standalone build,
the first two configurations were blocked before compilation, by a missing Ninja and by nvcc missing from the non-interactive PATH,
and the third built with the confirmed CMakeCache and absolute toolchain paths. This environment guesswork is also pinned in the execution register
as a recurrence guard. The full local Rust workspace tests and the real generation regressions of both adapters
have not yet been rerun for this code change, so no pass is claimed.

The first next action is to design a **contract that deterministically guarantees the required answer computation for medium/long at the product boundary**,
covering source, callers, output verification and the error terminal, and to pass the fix-removal mutations and the single-host exact cases
3/3. After that, seal the new corpus, generator, judge and remote executables in H0 v6 and
rerun distributed I0 exactly once. The current H0 v5 is historical evidence of the first run and does not approve
a new LOAD of the corrected source.
