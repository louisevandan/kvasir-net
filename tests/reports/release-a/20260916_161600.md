## 원인 분리와 반증

동일 GGUF의 독립 llama-server를 Spark에서 실행했다. upstream pin `451b89b`에 작업 트리
변경을 결속한 빌드이며 이 PC에서 컴파일하거나 추론하지 않았다. 이전 입력을 그대로 보낸
medium도 동일한 오답 JSON을 냈고 long도 오답이었다. 따라서 이 두 오답에 대해
분산 transport만 원인이라는 가설은 반증됐다. 모델별 GGUF chat template의 no-thinking
assistant 접미부는 `<think>\n\n</think>\n\n`인데 corpus 생성기는 `<think></think>`를
붙였다. 이를 정확한 접미부로 고치고 정적 반례를 추가했다. 단, 이것을 **충분 원인으로
확정하지 않았다.**

수정된 corpus v2는 원격 원본 tokenizer로 64건 전부 다시 토큰화했다. 기존 대비 64건의
오라클·원자료·arrival·class는 동일하고 프롬프트 해시만 전부 달라졌다. 매체 원자료는
`target/release-a-i0-v5-20260916/corpus-v2/`, `corpus.json` SHA-256
`e9760a98ec190e537ff3203f01ea45e7d73033ced14be52d09a768a7451f815f`, tokenizer
SHA-256 `fba7e68f6442312155c355e015de2227e9d30c725e1f310bbca6e76cd24a6311`이다.
이 v2는 새 H0로 봉인되지 않았으므로 분산 실행에 투입하지 않았다.

수정된 case-00/04/06의 정확 프롬프트를 같은 standalone 모델에 각각 2,782/32,000/100,038
token으로 순차 제출했다. 세 응답 모두 보낸 프롬프트와 수신 프롬프트가 byte 일치하고 EOS였다.
자동 capability gate의 실제 결과는 `case-00 PASS`, `case-04 oracle_mismatch`,
`case-06 invalid_json`으로 **1/3**이다. medium은 첫 행 78,400 mW를 반환했고 정답은
40,768 mW다. long은 JSON 코드 펜스와 틀린 산술·경보를 반환했다. 응답 JSON SHA-256은
case-00 `d20f706887646cc151eb91bac0467d73b9d1930a83eb2adcad972afe5c359e01`,
case-04 `2f8785419b0268ba77ae6e52eaa8bfb455d461949de5dc139290414711570838`,
case-06 `2841abd701049bae3cba5655f4e5c92ff32c6a9de89e80af0adfa6cd842a1a8a`다.
`target/release-a-i0-v5-20260916/reference-v2/`에 원 응답을 보존했다.

단일 호스트의 model/input contract 자체가 이 정답 요구를 만족하지 않는다. `judge-reference-capability.py`
는 prompt·원본 토큰 수·EOS·JSON·오라클을 동시에 검사하고 독립 약화 7종을 거부한다.
이 gate가 GREEN이 되기 전에는 새 corpus로 분산 I0를 반복하지 않는다. 프롬프트 문구를
결과에 맞춰 바꾸거나 오라클을 느슨하게 하는 방식은 수용되지 않는다. 정확 산술을 제품 계약으로
요구한다면 입력에서 검증 가능한 값을 결정론적으로 계산·검증할 권위와 모델 출력의 책임을
설계한 뒤 모델 독립 시험에서 증명해야 한다. 모델 추측을 알고리즘으로 간주하지 않는다.

## 회수, 검증, 다음 첫 행동

standalone server는 실행 소유 PID 2995099·정확 executable·port 62005를 대조해 TERM했고
포트와 GPU compute process 0을 확인했다. Spark 보호 agent PID 1287453 및 :52005는 생존한다.
분산 첫 실행의 Spark/Mac20/Mac21 task agent·native·listener·터널은 별도 정상 회수 증거에
따라 0이다. 다른 세션의 프로세스는 종료하지 않았다.

로컬 정적 시험은 corpus 4/4, I0 judge self-test 12/12, capability gate 약화 7/7을 통과했다.
실제 capability gate는 의도대로 종료코드 1과 사례별 RED를 냈다. standalone 빌드 준비 중
처음 두 설정은 Ninja 부재와 비대화형 PATH의 nvcc 부재로 컴파일 전에 차단되었고,
세 번째는 확인한 CMakeCache/절대 toolchain 경로로 빌드했다. 이 환경 추측도 실행 장부에
재발 방지로 고정한다. 로컬 전체 Rust workspace 시험과 두 adapter의 실제 생성 회귀는
이번 코드 변경에 대해 아직 재실행하지 않았으므로 통과를 주장하지 않는다.

다음 첫 행동은 medium/long의 필수 정답 계산을 **제품 경계에서 결정론적으로 보장하는 계약**을
소스·호출자·출력 검증·오류 terminal까지 설계하고, 수정 제거 변이 및 단일 호스트 정확 사례
3/3을 통과시키는 것이다. 그 뒤 새 corpus·생성기·judge·원격 실행물을 H0 v6에 봉인하고
분산 I0를 한 번만 다시 실행한다. 현행 H0 v5는 첫 실행의 역사 증거이며 수정된 source의
새 LOAD를 승인하지 않는다.
