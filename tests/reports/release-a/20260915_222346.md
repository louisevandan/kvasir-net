## 구현과 경계

llama.cpp adapter가 version 1 `ResourceProfile`을 소유한다. LOAD 입력은 최대 요청 수, 요청 보존 bytes,
입력 token, 요청 하나의 bytes, 요청별/누적 출력 token, physical result, completion payload/retained,
edge retained, receipt retained의 11개 양의 정수 상한을 모두 요구한다. 누락·version 불일치·0·checked
integer overflow·내부 상한 불일치는 native 실행 전에 거부한다.

event runtime은 실제 completion mailbox, broker outbound edge, hop receipt store의 현재 남은 count/bytes를
조회해 profile과 대조한다. native READY는 B0에서 측정한 `max_physical_result_bytes`와 정확히 같아야 한다.
실행 경로는 요청 하나의 bytes/출력 token과 누적 입력·출력 token을 다시 검사한다. P4 공통 코어에는
llama.cpp tensor/model 타입을 넣지 않았고, event runtime은 backend 중립 snapshot만 adapter에 전달한다.

이 단계는 LOAD 시점의 잔여 용량 검사다. 동시 LOAD/실행 간 경쟁을 막는 reservation과 reservation의
publication 이동·퇴역은 B2에서 닫는다. broker dedupe receipt 수명 분리는 B3에 남아 있다.

## 실패와 원인

`first_pass=fail`이다. 첫 전체 시험은 이전 예기치 않은 종료 시 만들어진 손상 PDB를 LNK1285로 검출했다.
그 파일만 `.corrupt`로 격리한 다음 코드 시험은 전부 통과했지만 docs-lint가 `tools/README.md`의 혼합 EOL을
검출했다. 변경 파일을 기존 CRLF로 정규화한 최종 세 번째 gate가 exit 0이었다. 코드 로직 조정은 없었다.

원격 부족 경계에서 제품은 의도대로 1ms에 adapter 전용 `error-v2`와 failed-state 진단을 남겼다. 첫 harness는
공통 `error-v3`와 빈 node 목록을 기대해 실패했다. 실제 응답 계약과 failed-state 보존을 읽어 양성 실행을
별도 cold agent에서 한 번 수행했고 통과했다. 종료 스크립트는 Windows CRLF 때문에 종료 동작 후 exit 127을
냈으나, LF로 전송한 독립 사후 검사는 재종료 없이 exit 0으로 잔존 상태 0을 확인했다.

예기치 않은 종료 두 건 중 15:19:04 건은 모델 실행 없이 제한 없는 `cargo test` 두 개를 동시에 시작한 지
3분47초 뒤 발생했다. 16:18:52 건은 제한 없는 release build 뒤 로컬 llama.cpp/HF inference가 이어져 원인이
섞였다. 두 건 모두 Kernel-Power 41, bugcheck 0, power-button timestamp 0이며 직전 WHEA/GPU 오류는 없다.
따라서 전원 차단의 단일 하드웨어 원인을 단정하지 않고, 독립 증거가 있는 빌드 부하는 70% 이하로 제한하며
로컬 inference는 RTX 3090 하나만 노출한다.
