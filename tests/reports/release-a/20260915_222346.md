## Implementation and boundaries

The llama.cpp adapter owns the version 1 `ResourceProfile`. The LOAD input requires all 11 positive integer limits: maximum request count, request retention bytes,
input tokens, bytes per request, per-request/cumulative output tokens, physical result, completion payload/retained,
edge retained and receipt retained. A missing value, version mismatch, 0, checked
integer overflow or an internal limit mismatch is rejected before native execution.

The event runtime queries the current remaining count/bytes of the actual completion mailbox, the broker outbound edge and the hop receipt store
and compares them with the profile. Native READY must exactly equal the `max_physical_result_bytes` measured in B0.
The execution path re-checks the bytes/output tokens of each request and the cumulative input/output tokens. No
llama.cpp tensor/model types were added to the P4 common core, and the event runtime passes only backend-neutral snapshots to the adapter.

This stage is a remaining-capacity check at LOAD time. The reservation that prevents races between concurrent LOAD/execution, and the reservation's
move on publication and retirement, are closed in B2. Separating the broker dedupe receipt lifetime remains in B3.

## Failures and causes

`first_pass=fail`. The first full test run detected, as LNK1285, a corrupt PDB created during the earlier unexpected shutdown.
After quarantining only that file as `.corrupt`, all the code tests passed, but docs-lint detected mixed EOL in `tools/README.md`.
The final, third gate, after normalizing the changed file to its existing CRLF, exited 0. No code logic was adjusted.

At the remote shortfall boundary, the product, as intended, left an adapter-specific `error-v2` and a failed-state diagnosis in 1ms. The first harness
failed because it expected a common `error-v3` and an empty node list. After reading the actual response contract and the failed-state preservation, the positive run
was performed once on a separate cold agent, and it passed. The shutdown script exited 127 after the shutdown action because of Windows CRLF,
but an independent post-check transferred as LF confirmed 0 leftover state with exit 0, without shutting anything down again.

Of the two unexpected shutdowns, the one at 15:19:04 happened with no model running, 3 min 47 s after two unrestricted `cargo test` runs
were started at the same time. The one at 16:18:52 had mixed causes: an unrestricted release build followed by local llama.cpp/HF inference.
Both are Kernel-Power 41, bugcheck 0, power-button timestamp 0, with no preceding WHEA/GPU errors.
A single hardware cause for the power loss is therefore not concluded; build load, which has independent evidence, is capped at 70% or less, and
local inference exposes only one RTX 3090.
