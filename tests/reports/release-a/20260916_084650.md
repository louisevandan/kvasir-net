# Release A Qwen122B H1 first-run RED and execution spec correction

## Verdict

The first H1 run is **RED**. The 3-stage LOAD across three physical hosts and real inference did proceed, but within 30 minutes
only 8 of 64 requests finished through EOS and RELEASE. The other 56 have no terminal and no release, and a normal UNLOAD was also
rejected as busy. This run does not count as an H1 pass or a graceful recovery pass.

The cause is not a model stall. Unlike the resident 8 and per-request 30-minute limit, the quality mode of sealed H0 v1
submitted all 64 requests, 2,201,738 input tokens, at time 0. Even just before termination, the 8 active medium/long requests were still advancing
64-row prefill on all three stages. H1 is a quality corpus, and concurrent cold/sustained waves are owned by H2,
so the H0 v1 quality schedule violated the stage boundary. H0 v1 is preserved as historical evidence but is not used to approve a LOAD
of the new source.

## State and reclaim after the failure

After termination, INSPECT showed 56 pending requests/15,969,797 bytes and 1,211 transport failures on the head,
and 2 retained completions/268,435,456 bytes and 1 input on Mac20. Mac21 had 0 completions.
These values are observations from different stores and are not summed into a single cause.

The current event vocabulary has no explicit Cancel/Drain for a running v2 request, and NODE_UNLOAD is not a forced-cancel
command. Results were therefore not deleted just to make a normal UNLOAD succeed. As failure recovery, the task-owned
agent PIDs `2646538/30240/29702` and native PIDs `2649553/30347/29760` were stopped with TERM, and task ports
22150/23150–23152 and the tunnels were cleared. The protected `:52005` agent PIDs `1287453/69656/85992` were all re-checked
and are alive. This recovery is not an H1 pass or a graceful UNLOAD pass.

## Deterministic correction implementation

`max_in_flight` and a per-request-order `request_timeout_ms` were added to event-drive. H1 keeps the same LOAD
and submits the next corpus request only after receiving the RELEASE receipt. The open-loop waves of H2/H3/H7
do not set these values, which preserves the existing concurrency semantics. Before the run, the deadline vector's length and positivity and the
stage sequence capacity for max-in-flight are checked, and a Unix deadline is recorded on each submission event.

On remote Spark, the final candidate patch SHA-256 is `08391d02…` and the gate runner is `46c563c2…`.
`cargo fmt --check`, `cargo check -p p4-event-drive --tests` and the package tests, **106 PASS / 0 FAIL**,
passed in a single attempt.

In two independent copies with separate new targets, a single semantic line was removed and actually recompiled. With the RELEASE gate
removed, the actual drive test detected the submission of 2 requests; with the deadline recording removed, the same test detected the missing deadline
in the submission authority. Each test exited 101, with log SHA-256 `978ef4f5…` and
`5b953513…`. The mutation source SHA-256 values are `716e290b…` and `2d22fe3e…`.

## Runner failures and reuse rules

- The first mutation runner did not put Cargo on the non-login PATH and stopped before the tests. The second added `--exact` to a short test name
  and ran 0 tests. The third run, which pinned the canonical test list and `running 1 test`, detected both
  intended assertions. These do not count as repeated runs of the product candidate, but they are recorded as runner first-pass failures.
- The first preflight of the full gate stopped before the build because a person copied the full SHA of the baseline commit incorrectly. After switching to the exact value
  checked against local and remote `git rev-parse HEAD`, a single full run passed. From now on the runner must
  use generated inputs instead of hand-copied SHAs.
- The first real llama run reproduced L039 because the old native SHA `bdddd012…` did not emit the latest HELLO resource field.
  Only `4a14c867…`, after first checking the string capability and the source/hash in the B0 report, was run the second time,
  and it passed. Wire markers in an old binary are not evidence of compatibility with the current adapter.
- On HF shutdown, Ctrl-C in the PTY closed only the SSH connection and left the remote agent running. After checking the owner PID, executable, cmdline and listener
  together, TERM was sent only to that PID to reclaim it. The protected agent and other processes were not changed.
