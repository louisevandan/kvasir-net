# Release A Qwen122B H1 1차 RED와 실행 명세 교정

## 판정

H1 1차 실행은 **RED**다. 세 물리 host의 3-stage LOAD와 실제 추론은 진행됐지만 30분 안에
64건 중 8건만 EOS·RELEASE까지 끝났다. 나머지 56건은 terminal과 release가 없고 정상 UNLOAD도
busy로 거부됐다. 이 실행을 H1 또는 graceful recovery 통과로 세지 않는다.

원인은 모델 정지가 아니다. 봉인 H0 v1의 quality mode가 resident 8·요청별 30분 제한과 달리
64건, 2,201,738 input token을 시점 0에 전부 제출했다. 종료 직전에도 활성 중·장문 8건은 세 stage에서
64-row prefill을 계속 전진했다. H1은 품질 corpus이며 동시 cold/sustained wave는 H2가 소유하므로,
H0 v1의 quality schedule은 단계 경계를 위반했다. H0 v1은 역사 증거로 보존하되 새 source의 LOAD
승인에는 사용하지 않는다.

완료한 8건은 모두 short이며 각각 실제 prefill 2,780–2,789행, 생성 119 token+빈 EOS였다.

native 정지나 모델 오류로 재분류하지 않는다.

전체 evidence가 완성되지 않아 event-drive는 완료한 8건의 부분 row도 최종 RequestArtifact에
귀속하지 않았다. raw `batch_observations`에는 위 행이 남아 있다. 이는 실패 artifact의
`prefill_rows=0`이 실제 연산 0이라는 뜻이 아니며, H1 통과 수치로 복원하지 않는다.

## 실패 뒤 상태와 회수

종료 뒤 INSPECT에서 head는 pending request 56건/15,969,797 bytes와 transport failure 1,211건,
Mac20은 retained completion 2건/268,435,456 bytes와 input 1건을 보였다. Mac21의 completion은 0이었다.
이 값들은 서로 다른 저장소의 관측이며 한 원인으로 합산하지 않는다.

현재 event 어휘에는 실행 중 v2 요청의 명시 Cancel/Drain이 없고 NODE_UNLOAD는 강제 취소 명령이
아니다. 따라서 정상 UNLOAD 성공을 만들기 위해 결과를 삭제하지 않았다. 실패 recovery로 작업 소유
agent PID `2646538/30240/29702`와 native PID `2649553/30347/29760`을 TERM으로 종료하고 task port
22150/23150–23152와 터널을 비웠다. 보호 대상 `:52005` agent PID `1287453/69656/85992`는 모두 살아
있음을 다시 확인했다. 이 recovery는 H1이나 graceful UNLOAD 통과가 아니다.

## 결정론적 교정 구현

event-drive에 `max_in_flight`와 요청 순서별 `request_timeout_ms`를 추가했다. H1은 같은 LOAD를
유지하면서 RELEASE 영수증을 받은 뒤 다음 corpus 요청을 제출한다. H2/H3/H7의 open-loop wave는
이 값을 넣지 않아 기존 동시성 의미를 보존한다. deadline vector의 길이·양수 여부와 max-in-flight의
stage sequence capacity를 실행 전에 검사하고, 각 제출 event에 Unix deadline을 기록한다.

원격 Spark의 최종 후보 patch SHA-256은 `08391d02…`, gate runner는 `46c563c2…`다.
`cargo fmt --check`, `cargo check -p p4-event-drive --tests`, package 시험 **106 PASS / 0 FAIL**이
한 번에 통과했다.

두 독립 복사본과 서로 다른 새 target에서 의미 한 줄만 제거해 실제 재컴파일했다. RELEASE 게이트를
제거하면 actual drive 시험이 요청 2건 제출을 검출했고, deadline 기록을 제거하면 같은 시험이 제출
권위의 deadline 부재를 검출했다. 두 시험은 각각 exit 101이며 로그 SHA-256은 `978ef4f5…`,
`5b953513…`다. 변이 source SHA-256은 `716e290b…`, `2d22fe3e…`다.

같은 `08391d02…` patch의 전체 원격 회귀는 다음과 같다.

따라서 closed-loop/deadline **구현 자체는 수용**한다. H0 v2 재봉인과 H1 2차 실기는 아직 수행하지
않았으므로 Release A H1은 계속 RED다.

## 실행기 실패와 재사용 규칙

- 첫 변이 runner는 비로그인 PATH에 Cargo를 넣지 않아 시험 전 중단됐다. 둘째는 짧은 시험 이름에
  `--exact`를 붙여 0건을 실행했다. canonical test 목록과 `running 1 test`를 고정한 셋째 실행이 두
  의도한 단언을 검출했다. 제품 후보를 반복 실행한 횟수로 세지 않되 실행기 first-pass 실패로 기록한다.
- 전체 gate 첫 preflight는 기준 commit 전체 SHA를 사람이 잘못 옮겨 build 전에 중단됐다. 로컬·원격
  `git rev-parse HEAD`를 대조한 정확 값으로 바꾼 다음 한 번의 전체 실행이 통과했다. 이후 runner는
  수기 SHA 대신 생성 입력을 사용해야 한다.
- llama 실제 1차는 과거 native SHA `bdddd012…`가 최신 HELLO resource field를 내보내지 않아 L039를
  재현했다. 문자열 capability와 B0 보고의 source/hash를 먼저 대조한 `4a14c867…`만 2차에 실행해
  통과했다. 과거 바이너리의 wire 표식은 현재 adapter 호환 증거가 아니다.
- HF 종료에서 PTY의 Ctrl-C는 SSH 연결만 닫고 원격 agent를 남겼다. owner PID/executable/cmdline/listener를
  모두 대조한 뒤 그 PID에만 TERM을 보내 회수했다. 보호 agent와 다른 프로세스는 변경하지 않았다.
