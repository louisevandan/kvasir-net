## 반례·수정·실제 소비 경로

새 `probe-memory-plan.py`의 첫 버전이 config의 environment를 native 자식에게 전달하지 않았다.
Windows 로컬 기본 CUDA 순서에서 CUDA0은 RTX4080이었고, 같은 PLAN의 `fits:true`만으로는 이 오인을 잡지 못했다.
도구가 선언된 environment와 args를 전달하도록 수정하고 `--expect-device`의 정확한 장치 설명 검사를 추가했다.
native binary/config/실행 검사 스크립트 SHA와 raw stdout/stderr를 남기며 누락·중복 PLAN, timeout, 장치 불일치를 거부한다.
`public_plan_acceptance`와 `release_acceptance`는 항상 false다.

`probe-memory-plan-mutations.py`는 독립 source 복사본을 실제 Python으로 실행한다.
동일 native SHA `97003fc1077f18b34d7718c105da50e3e89323f99c6052ca11149268cc595aba`를 매번 확인했다.

| 실제 native 실행 | 결과 |
| --- | --- |
| config PCI_BUS_ID / 기대3090 | native exit0, 검사 exit0, 실제 설명3090 |
| 같은 config / 잘못된 기대4080 | native exit0, 검사 exit1 |
| environment 전달 제거 | 실제 설명4080으로 바뀌며 기대3090 검사 exit1; 수정 제거 검출 |
| 장치 검사 제거 / 잘못된 기대4080 | 검사 exit0으로 잘못 승인; baseline 거부 반례로 변이 검출 |

4실행과 제거 변이2종 PASS다. source 복사본 SHA를 각 실행 기록과 대조했다. native 재컴파일 변이가 아니라
Python 실행기 변이이며 native 소스/바이너리는 바꾸지 않았다. 첫 잘못된 장치 결과는 보존하고 별도 새 경로에서 재실행했다.
POSIX4host는 최종 Python helper, .17은 같은 환경 전달·native framing·기대 장치 검사·timeout을 기록한
별도 PowerShell 사전 검사로 실행했다. .17의 script SHA와 전체 script도 raw에 있다.

## 실행 환경과 정리

Windows SSH session0의 agent는 S:를 보지 못했다. .17은 기존 admin 대화형 세션에서 모델 접근을 확인한 뒤
숨김 일회성 Scheduled Task로 agent와 PLAN을 실행했다. 초기 quoting, script execution policy, 긴 SSH command 실패는
준비 실패로 보존했다. 최종 task만 process 범위 `-ExecutionPolicy Bypass`를 사용했고 시스템 정책은 바꾸지 않았다.
`.29/.17`의 새 agent41990에만 LAN 대역·정확한 실행 파일 경로로 한정한 임시 inbound rule을 사용했다.

검사 후 기록된 PID·실행 경로·Windows 시작 시각을 재확인하여 이번 agent만 종료했다.
첫 Windows cleanup은 자식 conhost를 발견해 중단했다. 해당 자식의 OS 실행 경로를 확인한 뒤 agent를 종료했고
conhost도 종료됐다. 최초 cleanup 실패와 최종 성공을 별도 보존했다. .17 일회성 task2개와 두 Windows의 임시 rule을
제거했다. POSIX4agent와 로컬 agent, SSH 유지 프로세스 종료 및7host41990 비청취를 확인했다.
최종 cleanup_error는 null이며 기존 배포/다른 agent는 유지했다. 배포 후보 파일과 raw는 보존했다.
