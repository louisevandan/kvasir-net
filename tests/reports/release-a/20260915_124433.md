# 9-machine cluster query and MI250 bidirectional SSH return verification

Compiled 2026-09-15 12:44 KST. [Test plan](../../plans/cluster-envelope-20260915.md).

## Verdict

The real event runtime of 9 physical machines was used without a model. In the normal state, LAN 7×7 and
local gateway/MI-A/MI-B 3×3 confirmed **542 responses and 20 rejections of an invalid context**.
The final query of the 10 agents also returned nodes=[], and owned processes, tunnels and temporary Windows tasks/firewall rules were cleaned up.
One PC ran separate agents for the LAN and for the tunnel, so there are 10 agent instances on 9 physical hosts.

This verifies normal delivery on the explicit ingress path. It is not automatic recovery after failure, node-derived output, model generation, or
acceptance of Release A as a whole. The test harness failures below and the state preserved after disconnection are part of the result.

## The actual path that reached MI250

Direct SSH from local to `OFFICE_GATEWAY_IP:5122/5222` timed out. From Ubuntu, TCP connections to both ports succeeded, and
login as `banya`/`banya2` respectively via local SSH with `-J hika@192.168.0.19` also succeeded.
What is confirmed, then, is **a difference in reachability by origin path**. Which device, router or firewall, blocks the direct path is not determined.

The local PC kept the SSH processes alive, and Ubuntu only relayed the SSH transport. P4 envelopes were not rewritten.
The gateway advertised `tcp://127.0.0.1:42010` as its address, and MI-A/B advertised 42011/42012 respectively.
After a separate test agent was started on the corresponding loopback port on each MI250, the following tunnel was used.

```text
ssh -J hika@192.168.0.19 -p 5122 -i <existing MI SSH key> \
  -o BatchMode=yes -o StrictHostKeyChecking=yes -o IdentitiesOnly=yes \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2 \
  -L 127.0.0.1:42011:127.0.0.1:42011 \
  -R 127.0.0.1:42010:127.0.0.1:42010 \
  -R 127.0.0.1:42012:127.0.0.1:42012 banya@OFFICE_GATEWAY_IP
```

The above shows the arguments; it is not PowerShell line-continuation syntax. In the test, a Python command that starts and waits for the remote agent
was appended to the end of the SSH command. If the remote agent is already running, `-N` can keep a forwarding-only connection.
MI-B is the symmetric configuration: SSH 5222, user banya2, `-L42012`, `-R42010`, `-R42011`.

The return goes OUTER → local gateway → forward tunnel → MI agent → reverse tunnel → gateway → OUTER.
Queries between the MI hosts also passed through the peer port's reverse tunnel → local → the peer's forward tunnel.
The ingress address, channel and generation were identical from request to response, and the MI250-specific GPU specs matched the direct per-target queries.
A plain `-L` alone cannot make the MI's return ingress address reachable.
The loopback addresses in this configuration are valid only inside the tunnel namespace and must not be deployed as is as addresses of ordinary LAN agents.
This does not implement an SSH creation/reconnection service in P4 itself.

## Failures and causes

1. In the first LAN run, the test client built event IDs from channel/sequence only, reusing the same ID across multiple
   ingresses/generations on the same channel. Direct, matrix and burst passed, but 14 generation-test groups and 7 reconnection groups failed.
   The 311 responses in the raw `lan-results-id-collision.json` were not added to the final 542 normal responses.
   The actual agent log showed `ConflictingDuplicate`. The harness was changed to use non-overlapping sequence ranges per connection.
   Input counts, generations and channel conditions were kept.
2. Running the fixed harness against the same agents did not restore the peer path. The raw
   `lan-results-retained-peer.json` is false with 63 responses and is excluded from the normal tally.
   `serve` in `entrypoints/agent/src/event_runtime/transport.rs` preserves the conflicting input and ends the connection.
   `deliver_outbound` caches a writer per destination and does not replace a failed writer.
   New events after `peer writer closed`, `result=uncertain` were also preserved.
   This is an explicit implementation that keeps later requests from automatically overtaking an uncertain earlier send,
   so no claim can be made that operation recovers without reconnection and settlement. A normal arm in which only the test LAN agents were restarted is recorded separately.
3. Creating a temporary local firewall rule failed for lack of administrator privileges. The rule was not assumed to exist,
   and real remote→local queries passed under the existing allow state. The test rules on m42/TUF were created and then removed.
4. Cleanup ran, but the evidence collector raised a TypeError because of a JSON extended object in a Windows PowerShell log string.
   The logs were reread as bytes/base64, and a read-only recheck of all hosts confirmed no PIDs, no tasks and no rules.

This verification is not an overall GREEN that hides failures. Normal envelope delivery and the SSH path passed;
explicit settlement/connection recovery for uncertain results and the existing FINISH defect remain. No change was made that adds a bypass address fallback to the envelope
or automatically resends uncertain events.
