# 9대 클러스터 조회와 MI250 양방향 SSH 반환 검증

2026-09-15 12:44 KST 정리. [시험 계획](../../plans/cluster-envelope-20260915.md).

## 판정

모델 없이 물리 9대의 실제 event runtime을 사용했다. 정상 상태의 LAN 7×7 및
로컬 gateway/MI-A/MI-B 3×3에서 **542개 응답, 20개 잘못된 문맥 거부**를 확인했다.
마지막 10개 agent 조회도 nodes=[]이며, 소유 프로세스·터널·임시 Windows task/방화벽 규칙을 정리했다.
하나의 PC에서 LAN용과 터널용 agent를 각각 실행했으므로 agent 인스턴스는10개, 물리 호스트는9대다.

이는 명시적 접수 경로의 정상 전달 검증이다. 장애 후 자동 복구, 노드 파생 출력, 모델 생성 및
전체 Release A 수용은 아니다. 아래 시험기 실패와 단절 이후 보존 상태도 결과에 포함한다.

## MI250에 도달한 실제 경로

로컬에서 `OFFICE_GATEWAY_IP:5122/5222`로 직접 SSH는 시간 초과였다. Ubuntu에서 두 포트 TCP 연결은 성공했고,
로컬 SSH의 `-J hika@192.168.0.19`로 각각 `banya`/`banya2` 로그인도 성공했다.
따라서 확인된 것은 **출발 경로별 접근성 차이**다. 라우터·방화벽 중 어느 장비가 직접 경로를 차단하는지는 미판정이다.

로컬 PC가 SSH 프로세스를 유지하고 Ubuntu는 SSH 전송만 중계했다. P4 엔벨롭을 재작성하지 않았다.
gateway는 `tcp://127.0.0.1:42010`, MI-A/B는 각각42011/42012를 자신의 주소로 광고했다.
두 MI250의 해당 loopback 포트에 별도 시험 agent를 실행한 뒤 다음 터널을 사용했다.

```text
ssh -J hika@192.168.0.19 -p 5122 -i <기존 MI SSH 키> \
  -o BatchMode=yes -o StrictHostKeyChecking=yes -o IdentitiesOnly=yes \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2 \
  -L 127.0.0.1:42011:127.0.0.1:42011 \
  -R 127.0.0.1:42010:127.0.0.1:42010 \
  -R 127.0.0.1:42012:127.0.0.1:42012 banya@OFFICE_GATEWAY_IP
```

위는 인자 표기이며 PowerShell 줄 연결 구문은 아니다. 시험에서는 원격 agent를 실행·대기하는 Python 명령을
SSH 끝에 붙였다. 원격 agent가 이미 실행 중이면 `-N`으로 전달 전용 연결을 유지할 수 있다.
MI-B는 SSH5222, 사용자banya2, `-L42012`, `-R42010`, `-R42011` 대칭 구성이다.

OUTER→로컬 gateway→정방향 터널→MI agent→역방향 터널→gateway→OUTER로 반환된다.
MI 간 조회도 상대 포트의 역방향 터널→로컬→상대 정방향 터널을 통과했다.
접수 주소·채널·세대는 요청부터 응답까지 동일했고 MI250 고유 GPU 사양도 대상별 직접 조회와 일치했다.
단순 `-L`만으로는 MI의 반환 접수 주소를 도달 가능하게 만들 수 없다.
이 구성의 loopback 주소는 터널 네임스페이스 안에서만 유효하며 일반 LAN agent의 주소로 그대로 배포하면 안 된다.
P4 자체의 SSH 생성·재접속 서비스 기능을 구현한 것은 아니다.

## 실패와 원인

1. 첫 LAN 실행에서 시험 클라이언트가 channel/sequence만으로 이벤트 ID를 만들면서 같은 채널의 여러
   ingress/generation에 같은 ID를 재사용했다. 직접·matrix·burst는 통과했으나 세대 시험14그룹과 재연결7그룹이 실패했다.
   원본 `lan-results-id-collision.json`의 응답311개를 최종 정상542개에 합산하지 않았다.
   실제 agent 로그는 `ConflictingDuplicate`였다. 시험기는 연결마다 겹치지 않는 sequence 구간을 사용하도록 수정했다.
   입력 수·세대·채널 조건은 유지했다.
2. 수정한 시험기를 같은 agent에 실행해도 peer 경로는 복구되지 않았다. 원본
   `lan-results-retained-peer.json`은 false, 응답63개이며 정상 집계에서 제외했다.
   `entrypoints/agent/src/event_runtime/transport.rs`의 `serve`는 충돌 입력을 보존하고 연결을 끝낸다.
   `deliver_outbound`는 목적지별 writer를 캐시하고, 실패 writer를 교체하지 않는다.
   `peer writer closed`, `result=uncertain` 이후 새 이벤트도 보존했다.
   불명확한 선행 송신을 후속 요청이 자동으로 추월하지 않게 하는 명시적 구현이며,
   재접속·정산 없이 운영 복구된다는 주장은 불가능하다. 시험용 LAN agent만 다시 시작한 정상 arm을 별도 기록했다.
3. 로컬 임시 방화벽 규칙 생성은 관리자 권한 부족으로 실패했다. 규칙이 생성됐다고 가정하지 않았으며,
   기존 허용 상태에서 실제 원격→로컬 조회가 통과했다. m42/TUF의 시험 규칙은 생성 후 제거했다.
4. 정리는 실행됐으나 Windows PowerShell 로그 문자열의 JSON 확장 객체 때문에 증거 수집기가 TypeError를 냈다.
   로그를 byte/base64로 다시 읽고 전 호스트를 읽기 전용 재점검해 PID 없음·task 없음·규칙 없음을 확인했다.

이번 검증은 장애를 감춘 전체 GREEN이 아니다. 정상 엔벨롭 전달·SSH 경로는 통과했고,
불명 결과의 명시적 정산/연결 복구와 기존 FINISH 결함은 잔여다. 엔벨롭에 우회 주소 fallback을 넣거나
불명 이벤트를 자동 재송신하는 변경은 하지 않았다.
