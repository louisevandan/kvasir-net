## 실행 환경 정정

사용자가 반복해서 명시한 계약은 SSH와 설치 앱의 파일 접근 환경이 다르며 모델 경로는 이 PC와 같은
`S:/models`라는 것이다. SSH에서 S:가 보이지 않고 UNC 직접 열기가 Windows1326 인증 오류였다는
사실을 설치 앱의 접근 실패로 확대했다. `Win32_ComputerSystem.UserName:null`과 quser 결과만으로
대화형 세션 부재를 단정한 것도 잘못이었다. 앱 process의 SessionId/owner와 실제 API를 확인해야 한다.

`.29`의 설치 앱은 사용자42mob/session1의 Linker supervisor `:18082`다. `/health`는 ok,
`/api/models/availability`는550B10개 shard 모두 available=true/missing=[],
`/api/models/inspect`는 실제 GGUF에서 nemotron_h_moe/108layer/8192embedding/512experts를 읽었다.
기존 설치 앱과 설정·프로세스는 변경하지 않았다. 첫 metadata 요청의400 응답은 준비 실패로 남기며,
후속 동일10개 shard 요청은200이었다. 경로와 모델·상한을 바꾸지 않았다.

기존 시험용 Rust agent `:52005`는42mob/session0/S4U이며 설치 앱과 다른 실행 환경이다.
그 agent에 만든 진단 node의 자식도 S:를 읽지 못했다. 이 진단 자식은 staged HELLO를 제공하지 않아
LOAD가 예상대로 ReadyFailed였으며 실제 모델 LOAD 성공으로 세지 않는다. 최초 DELETE는 failed 상태여서
거부됐고 UNLOAD는 아직 결속되지 않은 generation을 거부했다. 이후 이 진단 node에만 별도 로컬 Qwen 파일로
정상 LOAD→UNLOAD→DELETE를 수행해 회수했고, INSPECT nodes=[]를 확인했다. 기존 agent를 재시작하지 않았다.
최초 회수 거부와 최종 회수 성공은 별도 raw다. receipt index의 보존을 자원 누수0으로 표현하지 않는다.

## 남은 PLAN

설치 앱과 같은42mob/session1에서 별도 숨김 일회성 task로 현재 봉인 native를 실행했다.
S: 모델을 그대로 읽고 stage0[0,24)/stage1[24,48)의 native complete/fits가 모두 true였다.
CUDA_DEVICE_ORDER=PCI_BUS_ID, CUDA0/1 RTX3090, seq8/ctx819200/batch128/ubatch64/F16/FA on,
CPU expert 배치를 유지했다. 원시 byte 값은 다음과 같다.

| stage | device required | host required | 결과 |
| --- | ---: | ---: | --- |
| 0 / CUDA0 | 14,813,148,288 | 75,105,305,888 | exit0, session1, complete/fits |
| 1 / CUDA1 | 14,059,241,344 | 81,308,681,248 | exit0, session1, complete/fits |

이로써 현재 native의8/8 stage 사전 검사가 확보됐다. 두 host 항목은 같은 `.29` RAM을 사용하며 별도
물리 pool로 취급하지 않는다. 공개 OUTER PLAN→LOAD의 모든 상한·실제550B allocation 또는 서비스 SLO
수용은 아니다. 각각의 `layer_device_expectations_checked:false`도 그대로 남긴다.
검사가 끝난 일회성 task `P4-Release-A-102259-Plans`만 삭제했다.

## 실기 직전 점유 확인

설치 앱 접근 정정과8/8 PLAN을 `b457e32aa`에 커밋·푸시한 뒤550B 실행 준비를 계속했다.
Spark의 기존 agent INSPECT에서 다른 작업 **브라우저 Qwen 122B 추론 시연**의
`studio-qwen122b-1789349924354-0`이 loading임을 확인했다. native PID39318은 그 작업의 기존
agent PID3662540 자식이며 이번 검사 소유가 아니다. 이 프로세스나 설치 앱을 종료하지 않았다.

마지막 Spark 가용 RAM은44,197,605,376bytes다. 이번550B stage2의 공유 pool 추정 요구는
device83,944,759,424 + host106,955,808 =84,051,715,232bytes이므로 동시 적재 여유가 없다.
현재7host 통합 실기는 이 별도 시연의 자원 점유 때문에 보류한다. SSH/NAS 접근 차단과 구분한다.
550B를 다른 배치나 낮춘 context로 실행하지 않았고 LOAD/SESSION/추론도 새로 시작하지 않았다.

최종 정리에서 진단용 로컬 Qwen 복사본을 제거했고, 이번 task0개/native 자식0개를 확인했다.
기존 시험용 agent PID5532와 설치 앱 PID12376의 실행 경로·시작 시각은 유지됐다.
